# 层 5 · 存储

> **本层不推荐任何一种形态。** 硬件条件差异太大，推荐"你该买什么"就是误导。
>
> 但不推荐 ≠ 不给判据。下面每种形态都标了"能承载什么 / 绝不能承载什么"——
> 那些不是偏好，是"否则会坏"。

## 一条贯穿全层的判据

**把数据分成两类，分别安置：**

| 类别 | 特征 | 对存储的要求 |
|---|---|---|
| **状态数据** | 数据库、索引、服务配置 | 苛刻：要原生文件系统、要稳定不掉线、要能保证写入顺序 |
| **体积数据** | 照片原图、影音、下载 | 宽松：大就行，掉一下不致命 |

**状态数据通常小得惊人**——十几个服务的配置卷加起来往往不到 1 GB。
而它一旦损坏，服务就起不来了。

> **最常见也最致命的错误：把数据库和媒体库放在同一块外接盘上。**
> 那块盘是为"大"选的，却承担了"苛刻"的职责。

## 枚举

| 值 | 形态 |
|---|---|
| `internal` | 机器内置盘 |
| `usb-portable` | 外接移动硬盘（USB 供电或单盘位） |
| `das-enclosure` | 外接硬盘柜（多盘位，独立供电） |
| `nas` | 网络挂载（另一台 NAS，走 SMB/NFS） |

四种可以**混用**，而且实践中通常就该混用。所以配置向量里 `storage` 是**多值字段**，
有几块写几块。

---

## 先读这一节：文件系统决定了这块盘能干什么

**这一节对上面四种形态一律适用**，不管盘是内置的、USB 的、硬盘柜里的还是网络挂载的。
**形态决定"掉不掉线"，文件系统决定"能承载什么"，两件事都要过。**

### 三类用途，要求递增

| 用途 | 例子 | 要求 |
|---|---|---|
| **只读媒体** | 影音库、只读挂载的图集 | 最宽松，exFAT / 网络挂载都行 |
| **可写媒体** | **相册的上传目录**、下载目录、同步目录 | 需要 POSIX 权限 —— exFAT 不行 |
| **状态数据** | 数据库、索引、服务配置 | 最苛刻 |

> ⚠️ **"媒体"不等于"只读"。这是本层最容易踩的一步。**
> 相册的照片库看起来和影音库一样是"一堆大文件"，但**它是容器要以非 root 身份
> 持续写入的目标**，而影音库通常只读挂载。
> 同一块 exFAT 盘，挂给影音服务只读没问题，挂给相册当上传目录就会出权限问题。

### 文件系统对照

| 文件系统 | 只读媒体 | 可写媒体（容器写入） | 状态数据 / 数据库 |
|---|---|---|---|
| ext4 / btrfs / xfs（Linux 原生） | ✅ | ✅ | ✅ |
| APFS / HFS+（macOS 原生） | ✅ | ✅ | ✅ |
| NTFS | ✅ | ⚠️ 跨平台驱动差异大 | ⚠️ 不建议 |
| **exFAT** | ✅ | ❌ **没有 POSIX 权限** | ❌ **绝对不行** |
| 网络挂载（SMB/NFS） | ✅ | ⚠️ 看挂载参数与服务要求 | ❌ **多数服务官方禁止** |

**exFAT 为什么不行**：没有 POSIX 权限、没有硬链接、日志能力很弱。
容器挂载 exFAT 卷时权限模型直接失效——症状是"服务起来了但一写就报权限错误"，
而且**挂载参数怎么调都绕不过去**，因为文件系统本身没有这个概念。
数据库还更糟：可能不立刻报错，而是**在异常关机后损坏**——最坏的失败方式。

exFAT 的存在理由是**跨平台通用**。如果这块盘要在多台机器间搬，它有价值——
但那就只能放只读媒体。

> **手上是一块 exFAT 盘、又要跑相册怎么办？**
> 只有两条路：① 重新格式化成原生文件系统（**会擦掉盘上现有数据**，
> 属于 `needs_human`，必须问用户）；② 只用它放只读媒体，可写的部分另找落点。
> **没有第三条路，别在挂载参数上浪费时间。**

---

## `internal` · 内置盘

| | |
|---|---|
| **能承载** | 全部——数据库、配置、系统。这是最可靠的落点 |
| **不能承载** | 只有容量限制，没有语义限制 |

**判据**：状态数据一律优先放这里。它总共不过 1 GB 量级，
别为了"整齐"把它跟媒体一起挪到外接盘上冒险。

**注意**：容量吃紧时先看能不能只把**体积数据**外移，而不是把整个服务目录搬走。

---

## `usb-portable` · 外接移动硬盘

| | |
|---|---|
| **能承载** | 媒体库、下载、冷备 |
| **绝不能承载** | **数据库。任何数据库。** |

### 为什么

USB 外接盘最大的风险不是盘体老化，是**意外断连**——线松了、供电不稳、
主机睡眠时总线掉电、系统更新后驱动变了。

对媒体文件，掉一次就是"这个视频暂时播不了"。
对数据库，掉一次可能就是**文件系统损坏**，而数据库还在往里写。

真实后果：盘一走，数据库进入崩溃重启循环，累计几千次——
而**原始数据一个字节都没丢**，SMART 也全绿。坏的不是盘体，
是它上面被反复异常断电磨损的文件系统。

→ 完整案例见 [坑典](../pitfalls/storage.md#数据库和媒体库同盘盘一走就崩溃循环)

### 文件系统同样要看

移动硬盘出厂常是 exFAT 或 NTFS。**掉线风险和文件系统限制是两回事，都要过一遍**——
见[上面的公共小节](#先读这一节文件系统决定了这块盘能干什么)。

### 如果只有这一块盘

那就**把数据库留在内置盘上，只把媒体文件放外接盘**。绝大多数服务都支持
"配置/数据库在一处、媒体库在另一处"的拆分配置。这是本层最重要的一句话。

---

## `das-enclosure` · 外接硬盘柜

| | |
|---|---|
| **能承载** | 媒体库、大容量数据；**取决于文件系统**，可能也能承载数据库 |
| **绝不能承载** | 落在 exFAT 上的数据库（见下） |

比移动硬盘稳定得多（独立供电、多盘位、通常总线更好），但**优势不是自动获得的**，
要靠两件事拿到：

### 分职

一柜多盘时给每块盘明确职责，而不是当成一个大池子：媒体一块、照片一块、
数据一块、冷备一块、备份目标一块。职责清晰后，某块盘出问题时你知道影响面在哪。

### 文件系统选型

见[上面的公共小节](#先读这一节文件系统决定了这块盘能干什么)——
**多盘位不会让 exFAT 变得能跑数据库。** 形态好不等于文件系统合格。

> ⚠️ **USB 直通进虚拟机**又是另一层脆弱。宿主直接挂载、再以目录方式共享给需要的服务，
> 通常比把整块盘直通进 VM 稳。

---

## `nas` · 网络挂载

| | |
|---|---|
| **能承载** | 媒体库、归档、备份目标 |
| **绝不能承载** | **数据库。** 多数服务的官方文档明确禁止 |

### 为什么

网络文件系统（SMB/NFS）在**文件锁定**和**写入顺序保证**上与本地文件系统语义不同。
数据库依赖这些语义保证一致性。跑在网络挂载上不一定立刻炸，
但**在网络抖动或断连时会静默损坏**。

这不是保守估计——Immich 等服务的官方文档直接写明数据库不得放在网络共享上。
**部署前查一遍你要装的服务的官方文档**，别靠推测。

### 其它注意

- **延迟**：媒体扫描、缩略图生成这类大量小文件操作，在网络挂载上会慢一个数量级
- **断连**：挂载点消失时，正在读写它的服务行为难以预测。挂载参数要考虑超时与重连
- **启动顺序**：服务启动时挂载可能还没就绪。需要显式的依赖或等待

## 组合示例（不是推荐，是说明判据怎么用）

假设：一台机器，内置盘 500 G，外接一块 4 T 移动硬盘。想跑相册和影音。

```
内置盘 500 G
├── 系统
├── 所有服务的配置与数据库          ← 状态数据，全在这
└── 缩略图/转码缓存（可重建，掉了不心疼）

外接 4 T
├── 照片原图
└── 影音库                        ← 体积数据
```

**关键点**：相册服务的数据库在内置盘，它的照片库在外接盘。
外接盘掉线时，服务会报"找不到文件"——难看，但**数据库完好，插回去就恢复**。
如果数据库也在外接盘上，掉一次就可能要从备份恢复。

---

## 备份

家用场景可以说"以后再说"。**工作室 / 微型企业不行——那里数据丢失等于停业。**

最低限度：

- **状态数据**（数据库、配置）定期导出，存到**另一块物理盘**上。这部分小，代价很低
- 很多服务自带定时数据库备份功能，**先确认它开着**，再考虑外部方案
- **备份要验证能恢复。** 没试过恢复的备份不算备份

详见 [`ops/backup.md`](../ops/backup.md)。

## 验收

```yaml
verify: |
  # 1. 确认数据库落点的文件系统类型
  #    Linux: df -T <数据库目录>
  #    macOS: diskutil info $(df <数据库目录> | tail -1 | awk '{print $1}') | grep 'File System'
  # 期望: 原生文件系统（ext4/btrfs/xfs/APFS），不是 exFAT，不是网络挂载

  # 2. 确认数据库落点不是外接易掉线的盘
  #    Linux: lsblk -o NAME,TRAN,MOUNTPOINT | grep <挂载点>
  # 期望: 不是 usb

  # 3. 拔盘演练（在还没有真实数据时做）
  #    卸载外接盘 → 确认服务报的是"找不到媒体"而不是数据库崩溃
  #    重新挂载 → 确认服务自行恢复
```

第 3 条最有价值，**而且只有在还没有真实数据时做才安全**。
建议在部署完成、灌真实数据之前跑一次。
