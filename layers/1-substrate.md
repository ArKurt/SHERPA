# 层 1 · 虚拟化底座

> 你手上那台机器，能承载什么形态的东西。这一层决定后面所有层的可选范围，先定它。

## 枚举

配置向量里 `substrate` 的合法取值：

| 值 | 含义 | 典型 |
|---|---|---|
| `vm` | 能跑虚拟机（硬件加速可用） | Mac（hvf）、开了 VT-x/AMD-V 的 x86、NAS 的虚拟化套件 |
| `container` | 只有容器运行时，跑不了 VM | 低配 NAS、部分 ARM 单板、云主机 |
| `bare-metal` | 直接在宿主 OS 上装服务，不套任何隔离 | 任何机器都可以，也可以与上面两者叠加 |
| `none` | 没有可当服务器的机器 | 只有笔记本和手机 |

`bare-metal` 与 `vm` / `container` **不互斥**——最常见的实际形态是"服务栈原生跑 + 旁路由
装在一个轻量 VM 里"（见 [锚点 B](../blueprints/b-hybrid-mini.md)）。

## 前置：这台机器得先有个能干活的系统

**本手册从"你已经有一个装好的类 Unix 系统"开始。** 下面这些不在手册范围内，
但它们是层 1 的实际前置——如果还没有，先解决它们再回来：

| 前置 | 说明 |
|---|---|
| **主机操作系统** | Linux 发行版 / macOS / NAS 厂商系统。手册不教装系统 |
| **SSH 或本机终端** | 后面所有步骤都要能敲命令 |
| **容器运行时** | 几乎所有服务模块的装法与 `rollback` 都基于容器（`docker compose`） |

### 如果这台机器现在跑的是 Windows

一台"闲置的旧笔记本"很可能是这种情况。**这是一个岔路口，必须问用户**：

- **重装成 Linux** —— 本手册的主路径，但**会擦掉盘上现有数据**
- **保留 Windows，用它自带的 Linux 子系统** —— 可行，但外接盘直通、
  开机自启、硬件转码都会更别扭，手册没有覆盖这条路径的坑
- **换一台机器**

⚠️ **重装系统是 `risk: high` + `needs_human`。** 不要替用户决定，
更不要在没确认盘上有没有要保留的数据之前动手。

### 选发行版

手册不推荐具体发行版。判据只有两条：

1. **你（或用户）会维护它** —— 长期跑的机器，会不会打补丁比装什么更重要
2. **容器运行时官方支持它**

> **本手册不覆盖装系统与装容器运行时的步骤。** 官方文档比任何二手教程都准，
> 而且它们变得比这份手册快。按官方文档装完，再回到这一层。

## 怎么判定

探测命令见 [`00-probe.md` §2](../00-probe.md#2a-虚拟化能力macos)。判定要点：

- macOS：`sysctl kern.hv_support` 为 `1` 表示这台机器可用 Apple 的 Hypervisor API，QEMU 能选 `hvf` 加速器。**性能自己在目标负载上测**——本手册没有可引用的基准
- Linux：以**当前这个用户能不能打开 `/dev/kvm`** 为准。打不开的原因不止一种——
  固件里的虚拟化开关、内核模块没加载、用户不在 `kvm` 组、嵌套虚拟化受限都可能。
  **别直接判成"BIOS 没开"**，按现场看到的报错继续查
- NAS：只看厂商套件装没装、能不能用。**不要根据型号猜**支持情况，各厂各代差异大

## 三个决定后续的判断

### 判断一：服务栈和旁路由要不要合体

这是本层最重要的一个决定，比"用哪个虚拟化"重要得多。

| | 合体（都塞进一个 VM） | 分开（服务原生 + 旁路由 VM） |
|---|---|---|
| 省事 | ✅ 一套系统管到底 | ❌ 两套要维护 |
| 性能 | ❌ 服务多套一层虚拟化 | ✅ 服务跑在原生 |
| 故障隔离 | ❌ **旁路由重启 = 所有服务重启** | ✅ 互不影响 |
| 存储 | ❌ 盘要直通进 VM，多一层脆弱 | ✅ 宿主直接挂 |

**合体的代价不是理论上的，[锚点 A](../blueprints/a-single-laptop.md) 上真发生过**：
一台 x86_64 老笔记本同时担了旁路由、容器宿主、代码仓库三个职能，17 个容器，
照片库和数据库落在同一块 USB 直通盘上；盘一走，数据库在空挂载点上反复初始化、
重启数千次。而重启旁路由这件事——本该是分钟级的小操作——会连带打断所有服务。

> 这是**一次**事故，不是所有合体方案的必然结果，当时的系统与数据库版本也没记下来。
> 它证明的是这条路径**会**这样坏，不是**必然**这样坏。

**分开的代价只是多维护一套。** 如果机器扛得住，分开。

### 判断二：宿主自己不要走 VM

不管选哪种形态：**宿主机自己的默认网关必须指向主路由，不要指向跑在它自己身上的旁路由 VM。**

否则会形成**启动依赖环**：开机时 VM 还没起来 → 宿主没网 → VM 依赖的东西拉不下来 →
VM 起不来。而你要修它，还得先有网。

> 成不成环取决于两件事：**VM 启动或修复需不需要联网**，以及**宿主有没有第二条默认路由**。
> 两个都否，才不会卡死。别赌这个——把宿主的网关写死指向主路由，成本是零。

### 判断三：先数网口

把一张**正在承载你管理会话**的网卡改成桥接，可能把这个会话一起中断掉。
**有第二条路（另一张网卡或 Wi-Fi）才能在出问题时不失联。**

实践形态：有线口做桥接与服务，Wi-Fi 留作管理生命线。只有一个网口时，
高风险操作必须在**物理接触得到机器**的场合做。

## 各底座要注意的

### macOS

- 硬件加速用 hvf。**性能在你自己的负载上验收**，本手册不给"接近原生"这类没有基准的说法
- ⚠️ **开了 FileVault，这台机器多半不能无人值守地开机**——断电之后要有人解锁，
  在那之前什么都没在跑，"改成系统级服务"也绕不过去。
  **但 Apple 芯片 + macOS 26 起有 SSH 远程解锁这条路**，能不能用取决于这台机器
  落在哪一档，**先查清再对用户承诺可用性**。
  判据与两个例外见 [`ops/boot-persistence.md`](../ops/boot-persistence.md#全盘加密会限制自恢复能力)
- ⚠️ 系统睡眠会让旁路由断线。如果这台机器要当别人的网关，睡眠策略必须先解决
- ⚠️ **macOS 上的"容器"和 Linux 上不是一回事。** 容器运行时**自己跑在一个
  Linux 虚拟机里**，所以"共用宿主内核"共用的是**那台虚拟机的**内核，不是 macOS 的。

  **但别把这句话压成"Mac 上容器都收不到局域网广播"——各运行时不一样，要分开看：**

  | 运行时 | 网络能力 | 能满足广播发现吗 |
  |---|---|---|
  | **Docker Desktop** | 4.34 起可以开 host networking，**但只在 L4 生效**，容器拿不到宿主接口，低于 TCP/UDP 的东西不支持 | ❌ **不能**据此承诺 mDNS/SSDP |
  | **OrbStack** | 官方写的是 host networking 让容器 *inherit the host's network namespace*，**语义和 Docker Desktop 不同** | ⚠️ 官方**没有**承诺广播一定正常，上游报告过随版本波动——**锁定版本、从局域网客户端实测**，别预先判死 |
  | **虚拟机（桥接网卡）** | 独立的局域网存在感 | ✅ 这是 Home Assistant 官方给 macOS 的路径 |

  📌 **所以"需要局域网存在感的服务在 Mac 上无解"是错的**——
  官方路径是**跑一台桥接网卡的虚拟机**。
  → Home Assistant 的具体做法见
  [`services/home-assistant.md`](../services/home-assistant.md#发现类集成需要能收到局域网广播)

  **这是选型问题，不是配置问题——在装之前就要定，不是装完再调。**

### Linux

- KVM 成熟，桥接直接用 bridge，不需要额外守护进程
- 注意发行版的网络管理器可能会在重启后重置桥接配置，要持久化

### NAS（厂商系统）

- 虚拟化与容器都是厂商套件，升级固件时可能被动
- ⚠️ **如果全屋客户端把跑在 NAS 上的那个 VM 当作唯一网关，那么 NAS 或这个 VM 一停，
  这些客户端就没有网关可走了。** NAS 本身有它自己的维护节奏
  （固件更新、RAID 重建、盘故障），这些时刻都会波及网络。
  评估时把这条算进去——见 [锚点 C](../blueprints/c-nas.md)

### 什么都没有（`none`）

**这是一个合法答案，不是失败。** 没有可当服务器的机器时：

- 想要代理 → 客户端各自装（[层 3](3-proxy-stack.md) 的 `client-side`），不需要旁路由
- 想要服务 → 先解决硬件，本手册的 [锚点 A](../blueprints/a-single-laptop.md) 说明了
  一台闲置笔记本能做到什么程度、代价是什么

不要为了"用上手册"而建议用户买硬件。

## 下一层

**先看你要不要代理**——这决定了接下来跳过多少层：

| [探针 Q2a](../00-probe.md#q2a-需不需要代理) 的答案 | 去哪 |
|---|---|
| **不需要代理**（只想跑服务） | **跳过层 2/3/4**，直接去 [层 5 · 存储](5-storage.md) |
| 需要，但只有电脑手机自己装客户端 | [层 3](3-proxy-stack.md) 选 `client-side`，跳过层 2 |
| 需要旁路由（有装不了客户端的设备） | 往下走 → [层 2 · 旁路由形态](2-gateway.md) |

⚠️ **别把"我要个家庭服务器"读成"我要代理"。** 这是两件事，
用户没提代理就是 `gateway: none` / `proxy: none`。
