# 层 6 · 公网入口

> **这一层可以整层跳过。** 只在局域网里用的话，跳过它能省掉域名、证书、
> 隧道账号一大堆事，攻击面也小得多。
>
> 先回答 [`00-probe.md` Q3](../00-probe.md#q3-要不要从外网访问)，再决定读不读下去。

## 枚举与选型

| 值 | 需要公网 IP | 暴露面 | 适合 |
|---|---|---|---|
| `none` | — | 无 | 只在家/办公室内用 |
| `tailscale` | ❌ 不需要 | **零公网暴露** | 只有你和同事要访问 |
| `tunnel` | ❌ 不需要 | 服务商托管的入口 | 要给外人访问，且没有公网 IP |
| `port-forward` | ✅ 必须 | **最大**——直接暴露在互联网上 | 需要直连性能（大流量媒体）|

### 先确认有没有公网 IP

很多家庭宽带给的是**运营商大内网地址（CGNAT）**，不是真正的公网 IP。
这种情况下 `port-forward` 根本不可能，无论怎么配都不通。

判断方法：查路由器 WAN 口拿到的地址，落在下面这些段里就是大内网：

| 网段 | 范围 |
|---|---|
| `100.64.0.0/10` | `100.64.x.x` – `100.127.x.x` |
| `10.0.0.0/8` | `10.x.x.x` |
| `172.16.0.0/12` | `172.16.x.x` – `172.31.x.x` |
| `192.168.0.0/16` | `192.168.x.x` |

⚠️ **`100.x` 要看第二段。** `100.64`–`100.127` 才是 CGNAT；
`100.0`–`100.63` 和 `100.128`–`100.255` 是**正常公网地址**。
只知道"开头是 100"判定不了，要拿到完整地址。

⚠️ **同一个网段还有另一个用途**：`100.64.0.0/10` 也正是 Tailscale 给节点分配地址
用的段。所以你可能在两个完全不同的地方看到 `100.x.x.x`——
一个是运营商给你的 WAN 地址，一个是组网工具的内部地址。**别混淆。**
判断 CGNAT 只看**路由器 WAN 口**拿到的那个。

**这决定了选项范围，先查清楚。**

### 是大内网？先别急着绕开它

在放弃端口转发之前，有两件事值得先试——**它们可能让问题直接消失**：

**① 向运营商申请公网 IP**

很多地区的家庭宽带**打客服就能开公网 IPv4**，或者至少能问清楚"现在有没有、能不能开"。
这是最省事的解法，而且不需要你在技术上绕任何弯。

⚠️ 但要知道两件事：公网 IP 通常是**动态**的（所以仍然需要动态 DNS），
而且部分地区/套餐确实不给。**问一次的成本很低，值得先问。**

**② 查一下 IPv6 是不是公网的**

**IPv4 走大内网、IPv6 却是公网地址**，这种情况相当常见。

```sh
# 在一台内网设备上
curl -s -6 <回显出口 IP 的服务>
# 拿到的地址如果不在 fc00::/7（本地）里，多半是公网 IPv6
```

如果是，那么**对支持 IPv6 的客户端**，你可以直接用 IPv6 直连——
不需要端口转发（IPv6 通常没有 NAT），只需要在主路由的防火墙上放行。

⚠️ 代价是**只有 IPv6 客户端能用**。对方在纯 IPv4 网络下（公司网、某些移动网络）
就连不上，所以它通常是**补充**而不是替代。

⚠️ 这也触及铁律①（要改主路由防火墙）——告诉用户怎么做，不代劳。

> 两条都不行，再回到上面的表：**组网工具或出站隧道，两者都不需要公网 IP。**

### 默认从 `tailscale` 开始考虑

如果访问者只有你自己和少数几个人：**组网工具是最简单也最安全的选择**。

- 零公网暴露——没有任何端口开在互联网上
- 不需要域名、不需要证书、不需要公网 IP
- 装上、登录、就能用

**不要因为"看起来不够专业"就跳过它。** 需要给不特定的人访问时才需要往下走。

## `tailscale` · 组网工具

**没有公网 IP 时最省事的方案。** 装上、登录、就能用——不需要域名、证书或公网 IP。

> 📖 官方文档：<https://tailscale.com/kb>
> （ZeroTier、自建 Headscale 是同类替代，判据相同，具体做法看各自文档）

### 装在哪：一台还是整个局域网

⚠️ **这里有个前提容易漏，漏了会白折腾。**

默认情况下，在一台机器上装 Tailscale，**只能访问那一台机器**。

想让"整个局域网都能通过它访问、而不用每台设备都装"，必须**两步都做**：

1. 在那台机器上**声明子网路由**：
   ```sh
   tailscale up --advertise-routes=192.0.2.0/24
   ```
2. **在管理后台批准这条路由** —— 没配 `autoApprovers` 的话**不会**自动批准。
   只做第 1 步而没批准，远端仍然只看得到这一台机器。

⚠️ 只做了第 1 步就以为成了，是最常见的失败方式——因为命令**没有报错**。

| 装在哪 | 得到什么 | 代价 |
|---|---|---|
| 服务器主机 | 访问这台机器上的服务 | 最直接，与旁路由解耦 |
| 旁路由 + 子网路由 | **整个局域网可达** | 旁路由挂了，远程访问也断 |
| 每台设备各装 | 各自可达，互不影响 | 设备多了很烦；电视之类装不了 |

两者可以都装。

### MagicDNS

开启后每台设备得到一个 `<设备名>.<你的 tailnet>.ts.net` 名字，不用记 `100.x` 地址。

⚠️ **这正是层 4 那个坑的来源** —— 这些名字会被透明代理的 fake-ip 吃掉，
症状是"用 IP 能连、用名字连不上"。
→ [坑典](../pitfalls/proxy-dns.md#之二--组网工具的域名被吃掉)

### exit node

可以指定某个节点当出口，让远端设备的**全部流量**从家里出去。
和本手册的旁路由是两件事，但会互相影响：
远端走 exit node 进来，再经旁路由出海，链路会绕一大圈。**先想清楚再开。**

### 与代理层的已知冲突

**必须在切网关之前解决：**

1. **路由层通常已经是对的** —— 代理插件默认把 `100.64.0.0/10` 列为直连，不劫持
2. **坏的是 DNS** —— `*.ts.net` 被代理的 DNS 吃掉，返回 fake-ip

修法见 [层 4](4-routing-dns.md#fake-ip-的三个坑)。
**如果你正靠它远程管理这台机器，务必先修再切网关**，否则切换瞬间就失联了。

### 验收

```yaml
verify: |
  # ★ 从【外网】跑 —— 手机关掉 Wi-Fi 走蜂窝数据

  # 1. 能连到装了 Tailscale 的那台机器
  ping -c2 <该机器的 100.x 地址>
  # 期望: 通

  # 2. ★ 声明了子网路由的话，确认局域网里【别的】机器也可达
  ping -c2 192.0.2.10        # 一台没装 Tailscale 的内网设备
  # 期望: 通。不通 = 后台没批准那条路由（最常见）

  # 3. 用名字而不是 IP 访问一次（验证 MagicDNS）
  curl -s -o /dev/null -w '%{http_code}\n' http://<设备名>.<tailnet>.ts.net:<端口>
  # 期望: 200。若失败而 IP 可以，见层 4 的 fake-ip 坑
```

## `tunnel` · 出站隧道

服务商（Cloudflare 等）提供的方案：本地跑一个客户端，**主动向外建立连接**，
外部访问经服务商转发进来。

**优点**：不需要公网 IP、不需要在路由器上开任何端口、自带 TLS 和 DDoS 防护。

### 不要固定隧道传输协议

隧道客户端通常支持多种传输协议并会自动选一个可用的。
**不要为了"稳定"把它锁死在某一个上——让它自动探测。**

这条建议同时也是**上游的默认行为**，所以照做不需要额外理由。

之所以特别写出来，是因为手册撞过一次：隧道全挂，强制成某一个协议后恢复；
几天后又全挂，而这次可用的**恰恰是刚才不通的那一个**。
一次经历、一个服务商——但它足以说明**协议可用性会随网络路径变化**
（运营商策略、中间设备、时段都可能影响），
而锁死协议等于把这个变化挡在了客户端能自愈的范围之外。
→ [坑典](../pitfalls/ingress.md#隧道全挂换个协议好了过几天又挂)

### 其它注意

- 隧道客户端本身要能自动重连、开机自启
- 配置和凭证要纳入版本管理或至少有备份，**但凭证绝不能进公开仓库**
- 服务商侧的 DNS 记录与本地配置是两处，改动时容易只改一边

## `port-forward` · 端口转发 + 动态 DNS

在主路由上把某个公网端口映射到内网服务。

> ⚠️ **这需要改主路由配置，触及铁律①。**
> 本手册**不代劳**，也不做端口转发的规划设计。
> 告诉用户需要做什么、以及风险是什么，由用户自己决定和操作。

### 暴露面是真实的

一旦端口开在公网上，它就会被扫描——**几小时内**就会有自动化探测来试弱口令和已知漏洞。
这不是危言耸听，是常态。

所以如果要走这条路，下面这些不是可选项：

- **只开必要的端口**，能少开一个是一个
- **前面必须有认证层**（见本页[「反向代理与证书」](#要做对的几件事)）
- **服务要保持更新**——暴露在公网的旧版本服务是最常见的入侵入口
- **不要转发管理界面**（路由器面板、NAS 管理页、代理控制面板）到公网

### 动态 DNS

家庭宽带的公网 IP 会变。需要一个定时任务把当前 IP 更新到 DNS 记录上。
更新频率取决于你能接受多久的中断。

## 反向代理与证书

一旦有多个服务要对外，就需要一个反向代理按域名分发到不同的后端。

### 要做对的几件事

- **认证层**：管理类界面前面必须有一层认证。别指望"没人知道这个地址"
- **证书自动续签**：证书有效期通常 90 天，**必须自动化**。手工续签迟早会忘，
  而忘了的表现是所有服务同时不可用
- **非法访问直接断开**：对不认识的域名请求直接拒绝，而不是回落到某个默认站点，
  可以显著减少扫描器拿到的信息

### 别忘了清理退役设备的残留

如果这台机器**曾经**把网关或 DNS 指向过某个后来退役的设备，而那个手工配置没清干净，
会留下一条指向不存在设备的路由。

症状极具误导性：**终端里 `curl` 后端正常，反向代理进程访问同一个后端却间歇性失败**，
表现为随机 502。原因是不同进程的路由选择优先级不同。

**这是本手册里最难诊断的一个坑**，完整案例与排查方法见
[坑典 · 幽灵路由](../pitfalls/boot-ops.md#幽灵路由退役设备留下的影子)。

## 验收

```yaml
verify: |
  # ★ 从【外网】验证，不是从局域网内
  # 用手机关掉 Wi-Fi、走蜂窝数据，或用一台外部主机

  # 1. 服务可达且证书有效
  curl -sI https://service.example.com | head -3
  # 期望: HTTP 200（或 401，如果有认证层——401 也是成功）

  # 2. 证书有效期
  echo | openssl s_client -connect service.example.com:443 -servername service.example.com 2>/dev/null \
    | openssl x509 -noout -dates
  # 期望: notAfter 在未来，且有自动续签在跑

  # 3. ★ 确认管理类界面没有裸奔
  curl -s -o /dev/null -w '%{http_code}\n' https://<管理界面域名>
  # 期望: 401/403。如果是 200，立刻停下来加认证

  # 4. 确认没开多余端口（从外部扫自己）
  #    只应看到你有意开放的那些
```

第 3 条不能省。**管理界面裸奔在公网上是最常见的严重错误**，
而它平时完全不影响使用，所以没人会发现。
