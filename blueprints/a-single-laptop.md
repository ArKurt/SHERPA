# 锚点 A · 老笔记本一肩挑

> 一台闲置的旧笔记本，同时当旁路由、容器宿主和代码仓库。
> **跑了很久，能用。但代价明确，而且是它自己暴露出来的。**

## 配置向量

```yaml
arch:      x86_64
substrate: [vm]                  # 一切都塞在这个 VM 里
gateway:   vm-openwrt            # 单臂旁路由
proxy:     shellcrash            # 订阅格式驱动的选择
storage:   [internal, usb-portable]
ingress:   tunnel                # 出站隧道，无端口转发、无公网 IP 依赖
services:  [jellyfin, immich, navidrome, aria2, home-assistant, sunpanel]
           # 当年实跑约 17 个容器，另有漫画库、聚合搜索、博客等
           # ——那几个本手册未收录，这里只列菜单里有的
```

**全部三个职能（旁路由 / 容器宿主 / git 仓库）都在这一个 VM 里。**

## 什么条件下选它

- 手上有一台闲置的 x86 笔记本，不想再花钱
- 想要一次到位——一套系统管到底，不用维护两处
- 服务的性能要求不高（家用媒体、相册这类）

## 它证明了什么

> ⚠️ 读这一节之前先看状态：**已验证 · 已退役**。
> 它能跑，但后来被换掉了，原因就是下面「代价」那一节。

**这条路真的能走通。** 十几个服务、透明代理、公网入口，全在一台十年前的笔记本上跑，
而且跑了很久。**不要因为硬件旧就否定它。**

笔记本当服务器还有个隐藏优势：**自带电池 = 自带 UPS**。市电闪断时它不会掉。

> ⚠️ **但别只记住这一句。** 笔记本当服务器的另一面是**电源管理**：
> 合盖睡眠、空闲睡眠、盖上就断网——这些默认行为和"7×24 提供服务"直接冲突，
> 而且是新手最容易忽略的一环。
> 电池解决的是"市电闪断"，解决不了"它自己睡了"。
> → [`ops/boot-persistence.md`](../ops/boot-persistence.md#睡眠)、
> [`00-probe.md` Q6](../00-probe.md#q6-这台机器会关机或睡眠吗)

## 代价（这才是这条锚点的价值）

### 代价一：旁路由重启 = 所有服务重启

三个职能在一个 VM 里，动其中任何一个都要重启整台。而旁路由是最需要频繁调整的部分
（改规则、换订阅、升级插件）——每次调整都会打断媒体播放、下载、家居自动化。

**这是合体形态最日常的痛，不是极端情况。**

### 代价二：数据库和媒体库落在同一块外接盘上

这是最严重的一条。相册服务的数据库和它的照片库都在同一块 USB 直通的移动硬盘上。

后果：那块盘被物理搬走之后，挂载点变成一个空的临时文件系统，
数据库以为自己是全新安装 → 开始初始化 → 失败 → 重启 → 再初始化，
**累计崩溃重启数千次**。

而 SMART 全绿——盘体没坏。坏的是它上面的文件系统，被反复的异常断电磨的。
**原始照片一个字节都没丢**，只是不在那儿了。

→ 判据见 [层 5](../layers/5-storage.md#usb-portable--外接移动硬盘)。
**如果只有一块外接盘，把数据库留在内置盘上。**

### 代价三：出网带宽被接口卡住

笔记本的网络接口速率可能远低于你的局域网能力。内网传输、媒体串流都会被它限住，
而这个瓶颈**不体现在 CPU 或内存监控上**，很容易查不到。

选之前先确认这台机器的网络接口速率。

### 代价四：容器镜像的架构

x86 机器上这不是问题。但如果日后要迁移到 ARM 机器（Apple Silicon、ARM NAS），
**所有镜像都要有 ARM 构建**。迁移前逐个查 manifest，别假设。

## 如果你正走在这条路上

不用推翻重来。按影响从大到小做两件事就能拿到大部分收益：

1. **把数据库挪到内置盘**，只留媒体在外接盘。代价很小（状态数据通常不到 1 GB），
   收益极大——外接盘掉线从"数据损坏"降级成"暂时找不到文件"
2. **如果这台机器还扛得住**，考虑把服务栈搬出 VM 跑在宿主上，
   只留旁路由在 VM 里 → 就变成了 [锚点 B](b-hybrid-mini.md)
