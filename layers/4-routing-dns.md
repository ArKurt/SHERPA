# 层 4 · 分流与 DNS

> 代理装起来只是开始。**决定好不好用的是这一层**，而它的坑比其它层加起来还多。
> 这一层的每个坑都有同一个特征：**症状不指向真凶**。

## 先确认：你到底是不是 fake-ip 模式

**别跳过这一步。** 本节余下的判据只对 fake-ip 模式成立，而**你未必在这个模式里**。

> ⚠️ **手册以前在这里写错过**，写的是"透明代理普遍默认开 fake-ip"。
> **mihomo 官方文档写的是 `enhanced-mode` 默认 `redir-host`，不是 fake-ip。**
> 之所以这个错误看起来很像真的：**插件预置配置和机场订阅经常主动开 fake-ip**，
> 所以很多人确实在 fake-ip 里——但那是配置给的，不是内核默认给的。

所以先去读**当前实际生效的那份配置**：

```yaml
dns:
  enhanced-mode: fake-ip        # ← 是这个值才往下读
  fake-ip-range: 198.18.0.0/15  # ← 你自己的段以这里为准，别照抄
  fake-ip-filter: [...]
```

- 是 `fake-ip` → 往下读，三个坑都跟你有关
- 是 `redir-host` 或没写 → **下面三个坑跟你无关**，直接跳到[「地区敏感服务」](#地区敏感服务必须钉死出口)
- 读不到最终配置（被插件覆写、被订阅覆盖）→ **先解决"我看到的配置是不是生效的那份"**，
  这本身就是这一层最常见的困惑来源

📌 `fake-ip-range` **以你自己配置里的那行为准**。`198.18.0.0/15` 是常见值，
不是固定值，各内核的默认也不一样——排障时按实际段去比对，别拿示例去比。

---

## fake-ip：为什么用它，以及它的代价

> 下面这一节假定你上面确认过是 fake-ip 模式。

开了 fake-ip 之后，DNS 查询不做真实解析，而是返回 `fake-ip-range` 里的一个假地址，
等流量真的发出来时，代理再按域名去建连接。

这么做是为了**让代理拿到域名**——如果客户端先解析出真实 IP 再连，代理就只看得到 IP，
按域名写的规则全都失效。

代价是：**任何"拿到 IP 后自己去连"的东西都会拿到假地址**。下面三个坑都是这个代价的变体。

---

## fake-ip 的三个坑

fake-ip 的代价是：**任何"拿到 IP 后自己去连"的东西都会拿到假地址。**
由此派生三个坑，配置这一层时必须一并处理：

| 坑 | 症状 | 要做什么 |
|---|---|---|
| **局域网服务访问不了** | 用 IP 能连，用主机名连不上 | 把本地域加进 fake-ip 过滤列表 |
| **组网工具域名被吃掉** | 组网工具 IP 通、名字不通 | DNS 策略指向它自己的 DNS **＋** 加进过滤列表 |
| **两套 DNS 劫持打架** | 解析结果随机、时对时错 | 关掉路由系统自带的 DNS 重定向 |

⚠️ 三条都有同一个陷阱：**填了列表不等于开了功能**——很多配置项还有一个总开关，
关着的时候列表白填。（实测过的一例：某套 Nikki 配置里 `mixin_file_content` 默认为 0。）
**别假定默认值，逐项去读当前生效的配置。**

⚠️ 自定义过滤列表时，**先确认这个数组是"追加"还是"整表替换"**——
两种语义都存在，取决于插件怎么做合并。替换语义下，你一自定义，插件内置的条目
就全不生效了，要一并补齐。**改之前先在临时副本上看一眼合并后的最终数组长什么样。**

⚠️ **把设备网关切到旁路由之前，先解决第二条。** 否则组网工具会在切换瞬间失联，
而你可能正靠它远程管理这台设备。

完整症状、原因与修法见
[坑典 · fake-ip 三连](../pitfalls/proxy-dns.md#fake-ip-三连)。





## 地区敏感服务：必须钉死出口

**这一节不是可选优化，对某些服务是功能前提。**

订阅的兜底通常是"其它所有流量 → 自动选择组"，而自动组按延迟挑节点。
**如果某个服务屏蔽了自动组可能落到的某个地区，它会在某天静默失效**——
没有配置变更、没有报错，表现可能只是"用着用着掉登录"。

已知实例：**Anthropic 与 OpenAI 的官方支持地区清单里都不含香港**（2026-08-28 核对）。
官方措辞是"不在支持范围"，不是"屏蔽"——但对你的效果一样：落到那儿就不工作。
各家流媒体同理。

⚠️ **这类清单会变，而且各产品、各账号类型可能不同。** 上面是某一天的核对结果，
不是永久定律——**自己去看当天的官方页面**，别拿这句话当依据。

⚠️ 如果这台旁路由要给 AI agent 用（**包括读这份手册的你自己**），这条是**功能前提**。

→ 完整症状与诊断见 [坑典](../pitfalls/proxy-dns.md#兜底链路把服务静默杀死)

### 做法

给这类服务**单独建一个选择组，手工指定地区，组里不放自动选项、不放被屏蔽的地区**。

```yaml
# 结构示意，具体语法见你所选插件的文档
proxy-groups:
  - name: <服务名>
    type: select
    proxies:
      - <你确认可用的地区>        # 第一个 = 默认选中
      - <备选地区 1>
      - <备选地区 2>
      # ⚠️ 故意不包含被该服务屏蔽的地区
      # ⚠️ 故意不包含"自动"——自动会漂，正是本组要规避的东西

rules:
  - 'DOMAIN-SUFFIX,<官方域名 1>,<服务名>'
  - 'DOMAIN-SUFFIX,<官方域名 2>,<服务名>'
```

把这条规则**放在规则表最前面**，确保它先于兜底命中。

### 别抄社区规则集

现成的规则集很方便，但**用之前看两件事：最后更新日期、条目数**。

**域名条目少**的服务，直接照官方当前的网络要求写死后缀，比引入一个会过期的外部依赖
可靠得多。找官方清单的关键词：`<服务名> network configuration` / `firewall allowlist`。

⚠️ 两件事别想当然：
- **写死之后要记核对日期，并定期回去看。** 别承诺"一年变不了一次"——你不知道。
- **官方某一个页面的清单未必覆盖全部产品面。** Web、API、桌面端、CLI 可能各有各的域名。

> 真实教训：核对某社区规则集时发现它只有 3 条、标注的最后更新已是一年多前，
> 且**没有覆盖官方说明里承载 OAuth 令牌刷新的那个域名**。
> 这种缺失的预期症状是**"用着用着掉登录"**——不是连不上，所以很难往规则集上想。
> 详见 [坑典](../pitfalls/proxy-dns.md#社区规则集过期漏掉关键域名)。

## 覆写与混入：怎么加自己的规则

订阅是别人给的，会定期更新覆盖。**你自己的规则必须放在订阅之外的地方**，
否则每次更新订阅就丢一次。

常见的做法是插件提供"混入 / 覆写"机制，把你的片段合并进订阅配置。
**这三件事各插件各版本都不一样，逐个去查你手上那个，别照搬**：

1. **合并语义是深合并还是替换？** 深合并意味着你新增的条目是**追加**，不会覆盖订阅原有的；
   替换意味着你写了什么就只剩什么。**猜错会丢掉订阅自带的规则集。**
   而且同一个插件里，不同的数组可能还不一样——实测过的一例：Nikki 会把
   `nikki-rules` 显式前置，其它数组走 yq 的深合并表达式。
2. **优先级顺序是什么？** 常见是"订阅 → 混入文件 → 界面配置"，后者覆盖前者——
   **但这是常见，不是规范**。
3. **有没有总开关？** 常见陷阱：混入文件**默认是停用的**（实测过的一例：
   `mixin_file_content` 默认 0）。只写文件不开开关 = 白写

### 改之前先 dry-run

高风险配置（这台机器是别人的网关）改动前，**先在临时副本上跑一遍合并，检查结果**：

```sh
# 思路示意——具体命令取决于插件
# 1. 把当前生效的配置复制一份到临时位置
# 2. 对副本执行与插件相同的合并逻辑
# 3. 检查关键数字：
# - 规则总数 = 订阅条数 + 你新增的条数？ 验证是追加不是替换
# - 规则集数量 = 订阅原有数量？ 验证深合并没吃掉东西
```

数字对不上就别提交。

## 辅助取证：问内核，别信配置文件

**配置文件里写了什么不算数，内核实际在用什么才算数。**

> ⚠️ **但这一节不是验收。** 内核状态只能证明"规则加载了"，
> 不能证明**电视拿到了正确的 DNS 结果**。正式验收见本页末尾的「验收」一节，
> 那里的每条都从客户端跑。控制接口是**出问题时的取证手段**，不是通过标准。

mihomo 提供一个 HTTP 控制接口，可以直接问它。
**但你的插件有没有把它暴露出来、监听在哪个地址端口、有没有开密钥，
以插件的配置为准**——不是每套都开着。

> ⚠️ **控制接口的密钥不要写进命令行。** 写成 `-H "Authorization: Bearer $TOKEN"`
> 也不行——shell 展开后值仍然进 argv。让它走 curl 的配置（stdin）：

```sh
read -rs API_SECRET

api() {                       # $1 = 接口路径
  printf 'header = "Authorization: Bearer %s"\nsilent\n' "$API_SECRET" \
    | curl -K - "http://192.0.2.4:9090/$1"
}

api rules        # 生效的规则表（确认你的规则在最前面）
api proxies      # 各代理组当前选中了谁
api connections  # ★ 最有用的：真实连接命中了哪条规则、走了哪条链

unset API_SECRET; unset -f api
```

### 对照实验才算证明

静态看配置不算验证。要**同一时刻两条流量分道**才算证明规则生效：

1. 故意把自动组切到"坏"的地区，构造最坏情况
2. 同时产生两类流量：一条应命中你的专用规则，一条走兜底
3. 查 `/connections`，确认两者走了**不同的链**
4. 再用回显 IP 的服务确认两者的**出口地区确实不同**

只有这样才证明"自动组漂移不会影响被钉死的服务"——这正是你做这件事的目的。

## 验收

```yaml
verify: |
  # ★ 全部在【客户端】上执行，网关已指向旁路由。
  #   内核控制接口的输出【不能】代替下面任何一条。

  # 1. 直连目标：被你的规则判为 DIRECT 的域名，确认没走代理
  curl -s https://<回显出口 IP 的服务 · 你规则里判 DIRECT 的那个>
  # 期望: 你自己的公网出口，不是代理节点的

  # 2. 代理目标：被你的规则判为走代理的域名，确认走了、且落在预期地区
  curl -s https://<回显出口 IP 的服务 · 你规则里判走代理的那个>
  # 期望: 出口 IP 是代理节点的，且落在你为它指定的地区
  #
  # ⚠️ 1 和 2 必须是【两个不同的目标域名】，命令本身是一样的。
  #    怎么挑这两个域名、怎么确认出口地区，见下面「怎么准备这两条」。
  #    透明代理下「走不走代理」由规则按【目标】判定，不由 curl 的参数决定——
  #    没有任何 curl 开关能让同一个域名这次走代理、下次不走。
  #    两条填了同一个地址的话，你测的是同一件事，不管结果如何都证明不了分流生效。

  # 3. ★ 本地域没有被换成 fake-ip 【只有 fake-ip 模式才需要测这条】
  nslookup <你的内网服务域名>
  # 期望: 返回真实内网地址；【绝不能】落在你配置里那个 fake-ip-range 内
  #
  # ⚠️ redir-host 模式下这条必然通过，测了也证明不了任何事。
  #    先按本页开头确认自己是哪种模式，别把一条恒真的检查当成验收通过。

  # 4. ★ 组网工具的域名（装了、且是 fake-ip 模式才测）
  nslookup <节点名>.<你的 tailnet>.ts.net
  # 期望: 返回真实 100.64.0.0/10 地址，不是 fake-ip 段里的地址

  # 5. 地区敏感服务真的钉住了（构造最坏情况）
  #    手工把自动组切到一个被该服务屏蔽的地区，然后：
  curl -s -o /dev/null -w '%{http_code}\n' https://<该服务域名>
  # 期望: 仍然正常。若此时失败，说明规则没生效或没排在兜底之前
```

### 怎么准备验收第 1、2 条

这两条要你自己找两个目标，手册不能替你填——**填死了就成了照抄，而你的规则表未必这么判**。
但挑法是有章可循的：

1. **先看你自己的规则表，挑两个必然落在不同分支的域名。**
   在内核的控制接口上查 `/rules`，或直接读生效配置——
   找一条明确 `DIRECT` 的、和一条明确走代理的，各取一个域名。
   **别凭印象猜某个站"应该"直连。**
2. **两个目标都要能回显出口 IP。** 挑那种"访问它就告诉你我看到的来源 IP 是什么"的服务。
3. **回显服务通常只给 IP，不给地区。** 要判断"落在预期地区"，需要**另做一步**：
   用一个 IP 归属查询把第 2 条拿到的 IP 映射成地区，
   或者干脆挑一个**连地区一起回显**的端点，省掉这一步。
4. **先记下不走代理时的基线**（把客户端网关切回主路由测一次），
   否则第 1 条"你自己的公网出口"你根本不知道该是什么。

### 没有终端的设备怎么验收

上面每一条都要在客户端上敲命令——**而电视、游戏机、投影仪一个都敲不了**。
偏偏它们才是旁路由存在的理由（[层 3](3-proxy-stack.md#选型判据旁路由拿不到进程身份)）。
只验了电脑就宣布"全屋代理完成"，**恰好漏掉了目标本身。**

对这类设备，用**它自己看得见的行为**作为主判据：

| 设备 | 怎么验 | 期望 |
|---|---|---|
| 电视 / 机顶盒 | 用它的浏览器打开一个**回显出口 IP 的页面**，把屏幕上的 IP 读出来 | 是代理节点的出口，不是你家的公网 IP |
| 游戏机 | 同上（多数有内置浏览器）；没有浏览器的，看那个**你本来就想让它用的服务**能不能正常工作 | 能用 |
| 只有 App 的设备（智能音箱等） | 看它依赖的功能是否正常 | 功能可用 |

**然后**再去内核的控制接口上按这台设备的 IP 过一遍连接列表，
确认它的流量确实出现在那里、走的是你期望的那条链。

⚠️ **顺序不能反。** 控制接口只能证明"规则加载了"，
证明不了这台电视真的借到了道——那正是[「核能出海 ≠ 客户端能借道」](3-proxy-stack.md)
那条教训的原话。**设备侧看得见的结果是主判据，控制接口是佐证。**

📌 **每类设备至少验一台真机。** "在我电脑上是好的"对这一层没有意义。

⚠️ **第 3、4 条是这一层最容易漏的**，而且它们的失败方式是"某些设备连不上局域网服务"，
完全不指向 DNS。

⚠️ **第 5 条要主动构造最坏情况。** 不构造的话，它会在几周后的某个凌晨自己发生。

## 保留网段：什么不该被代理

确认这些是直连、不劫持的：

| 网段 | 用途 |
|---|---|
| `192.0.2.0/24`（你的局域网） | 本地服务互访 |
| `100.64.0.0/10` | Tailscale 等组网工具的 CGNAT 段 |
| `fc00::/7` | IPv6 唯一本地地址 |
| `127.0.0.0/8`、`::1` | 本机 |

**别依赖插件默认值**——从**最终生效的规则**里逐条确认这几段是直连、没被劫持。
自定义过规则之后尤其要回头看一遍。

## 回退

这一层的所有改动都应该能**一条命令退回**，且退回不依赖刚改坏的链路。
改之前先确认：

- 混入/覆写有总开关 → 关掉开关就回到订阅原样
- 配置文件改动前留了备份
- 到旁路由的管理通道是**局域网直连、不经代理**

最后一条最重要：这台机器是别人的网关，配置错会断网，**但你必须还进得去**。
