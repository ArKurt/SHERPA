# 层 2 · 旁路由形态

> 铁律①在这一层展开。读之前先确认你接受它。

```
① 只做旁路由，不做软路由。
   不碰 PPPoE、不接管寻址、不做端口转发规划、不改主路由配置。

② DHCP 只由主路由负责。
   旁路由不发地址，最多被指为客户端的网关 / DNS。
```

## 什么是单臂旁路由

一台设备，**只有一个网络接口**，接在现有局域网里，拿一个和其它设备平级的静态 IP。
它不是网关设备，主路由仍然是网关。客户端**自愿**把网关/DNS 指向它，流量绕道进来、
被透明代理处理、再原路出去。

```
        互联网
          │
      ┌───┴────┐
      │ 主路由  │  ← 继续负责 PPPoE / DHCP / Wi-Fi，本手册不碰
      │192.0.2.1│
      └───┬────┘
          │  局域网 192.0.2.0/24
   ┌──────┼───────────┬─────────────┐
   │      │           │             │
┌──┴──┐ ┌─┴────────┐ ┌┴─────────┐ ┌─┴──────┐
│ 电视 │ │  旁路由   │ │ 工作机    │ │ 其它设备│
│      │ │192.0.2.4 │ │198.51.100.7│ │        │
└──┬──┘ └─┬────────┘ └┬─────────┘ └────────┘
   │      │  ▲         │
   └──────┼──┘         │   ← 只有"网关指向 .4"的设备绕道
          └────────────┘
```

**"单臂"指的是流量从同一个接口进、同一个接口出**（hairpin）。这是它最省事的地方——
不需要改物理接线，也不需要主路由配合做任何路由。

## 为什么绝不能发 DHCP

旁路由一旦开 DHCP，就会和主路由**抢着回应**客户端的地址请求。谁先回应谁说了算，
结果是随机的：有的设备拿到主路由的配置，有的拿到旁路由的，同一台设备重启后还可能换一边。

症状是"时好时坏、换个设备又不一样"——这是最难诊断的一类故障，因为它不稳定复现。

所以：**建好旁路由后第一件事就是确认它的 DHCP 服务是关的**，不是"没配"，是明确关掉。

## 枚举

| 值 | 形态 | 何时选 |
|---|---|---|
| `vm-openwrt` | OpenWrt 系发行版跑在虚拟机里，单臂 | `substrate: vm`。**本手册的主路径** |
| `container-macvlan` | 容器 + macvlan/独立 IP | 只有容器、跑不了 VM 时 |
| `dedicated-box` | 独立物理小盒子 | 想要旁路由与服务器彻底解耦 |
| `client-only` | **不做旁路由**，客户端各自装代理 | 只有一两台设备要用 |
| `none` | 不需要 | |

### 先问一个问题：你有装不了客户端代理的设备吗

这个问题决定了要不要做旁路由，比任何技术对比都重要。

**旁路由的价值就在于"这台设备本身装不了代理"** —— 电视、游戏机、投影仪、IoT、
别人的手机。这类设备你没法在上面装客户端，只能让它们绕道。

| 你的设备 | 结论 |
|---|---|
| **有**电视 / 游戏机 / IoT 要走代理 | **需要旁路由**。这是它唯一不可替代的场景 |
| 只有电脑和手机（都能自己装客户端） | **`client-only` 更简单也更强**，见下 |
| 压根不需要代理 | `gateway: none`，整个层 2 跳过 |

### `client-only` 什么时候更强

如果要走代理的设备**都能自己装客户端**（电脑、手机、平板）：

- 客户端代理**能按进程分流**，旁路由**不能**（[层 3 · 坑二](3-proxy-stack.md)）
- 装挂了只影响那一台，不影响别人
- 不需要静态 IP、不需要动主路由、**没有单点故障**
- 出门在外一样能用，不依赖家里那台机器还开着

⚠️ **不要把"我的电脑和电视能用就行"直接读成 `client-only`。**
这句话里的"电视"恰恰是需要旁路由的那一半。而"能用就行"通常是在说
**"别影响家里其他人"**——那是接管范围的问题，不是要不要做旁路由的问题。
两件事分开问清楚。

### `vm-openwrt` —— 主路径

选 OpenWrt 系（ImmortalWrt / OpenWrt / iStoreOS 等下游发行版）的理由：

- 透明代理需要的内核模块（tun、nftables、tproxy）开箱就带，不用自己编
- 生态成熟，代理插件都是围绕它做的
- 是完整的路由系统，出问题时诊断工具齐全

**发行版差异不大，挑一个有你要的架构镜像的即可。** 下游发行版（加料版）比原生 OpenWrt
少踩"缺内核模块"的坑，但也更容易在升级时出意外。

### `container-macvlan` —— 只在跑不了 VM 时

容器要当旁路由必须有**独立的局域网 IP**，所以需要 macvlan 或等价的网络模式。
默认的 bridge/NAT 模式不行，host 模式更不行。

⚠️ **已知的三类麻烦**，选之前想清楚：

1. **内核不是你的** —— 容器共用宿主内核。宿主内核缺 tproxy/tun 模块、或厂商 NAS 精简过，
   代理就是起不来，而且报错往往指向别处
2. **macvlan 默认把宿主隔离在外** —— 宿主机访问不到自己上面 macvlan 容器的 IP。
   这会让"宿主上的服务反代旁路由面板"这类需求直接失败。
   要让宿主够得着，得按 Docker 官方给的做法另外设计（给容器再接一张 bridge，
   或在宿主上建一个 macvlan 接口），**并且验收**——别默认它通
3. **重启与自愈** —— 容器重启后网络配置、防火墙规则要能自己回来，这需要额外做工作

**host 网络模式是明确的反例**：它让代理直接接管宿主的网络栈，和 NAS 自身的职责打架，
且没有独立 IP 可指。不要用。

## 推进顺序（关键）

**不要一步到位。** 安全的顺序是：

```
① VM 起在隔离网络里（NAT / user-mode），验证系统能起、代理内核能装能跑
   —— 此时对局域网零影响，配坏了也不会有人断网
        ↓
② 切桥接，拿到独立的局域网 IP，确认 LuCI / SSH 可达
   —— 这一步会短暂中断被桥接的网卡，先备好管理生命线
        ↓
③ 只用一台测试设备把网关指过去，实测通
        ↓
④ 实测通过后，才考虑扩大范围
   —— ⚠️ 若要扩到全屋，先做下面那一节「扩到全屋之前必须做的一步」
```

第①步和第②步之间隔一晚上都没关系。**第②步安排在你能物理接触到机器、且家里人不急着用网
的时候做。**

## 必须问用户的

### 静态 IP 怎么来

> 📌 **不做旁路由也需要这一步。** 只要有服务要被别的设备访问（相册、影音、面板），
> 那台服务器就需要一个不变的地址——否则手机 App 里填的地址过几天就失效了。
> 下面的做法对"服务器主机"和"旁路由"同样适用。


旁路由需要稳定地址。两条路：

- **主路由绑定**（推荐）：按 MAC 绑定固定地址。**告诉用户怎么做，不要代劳** —— 铁律①
- **旁路由内部配静态**：可行，但要确认这个地址在主路由的 DHCP 池之外，否则早晚撞车

最稳的做法是**两边都做**：VM 内配静态，主路由再按 MAC 绑同一个地址。互为保险。

### 谁走旁路由

见 [`00-probe.md` Q2](../00-probe.md#q2c-接管范围多大)。

⚠️ **全屋默认是 `risk: high`。** 它把旁路由变成单点故障——它挂了全家断网，
包括根本不在乎代理的人。工作室 / 微型企业尤其要谨慎：**断网即停工**。
那里更该用"指定设备走"。

### 扩到全屋之前必须做的一步

**"全屋默认"的做法是在主路由的 DHCP 里把下发的网关改成旁路由。
那是发给整个地址池的——谁还在吃 DHCP，谁就会被改到。**

包括**跑着这台旁路由 VM 的宿主自己**。它如果还在吃 DHCP，续租之后默认网关就会
指向一台由它自己承载的虚拟机，于是触发[层 1](1-substrate.md) 写过的开机死锁：
开机时 VM 还没起 → 宿主没网 → 宿主上依赖网络的容器 / 套件起不来 →
而你这时候恰恰需要宿主的网络去修那台 VM。

**第 0 步：先确认主路由改得了。**
"全屋默认"整个建立在"能改 DHCP 下发的网关"这件事上，
而**不少运营商光猫把这些选项锁了**。改不了的话这条路直接不通——
只能逐台手动指网关，或者换一台自己的路由器做主路由。
**这要在动手之前确认**（[探针 Q2c](../00-probe.md#q2c-接管范围多大)），
不是做到一半才发现。

**手册别处只说了"宿主不算在内"，那是判据，不是步骤。**
下面这张表才是步骤——扩大范围前逐台确认它们已经被"锁出"DHCP 下发的网关：

| 设备 | 要做的事 |
|---|---|
| **承载旁路由 VM 的宿主** | 改静态，网关写死主路由。**这条没得商量** |
| 不该走代理的设备（工作机、打印机、IoT / 智能家居） | 改静态，或在主路由上单独给它们留策略 |
| 主路由自己 | 不吃自己的 DHCP，不用管 |

📌 **扩到全屋本来就是 `needs_human`。问用户的时候把这张表一起念一遍，
不要只问"要不要全屋"。**

### 宿主上已有的服务，跟着宿主直连

宿主的网关必须指主路由（上面那条硬约束），**所以它上面已经在跑的容器也一起直连**——
下载器、备份任务、拉镜像，全都不经过旁路由。

这**通常正是你想要的**（下载器走代理会把代理带宽吃光，影响全家）。
但要跟用户确认清楚，因为它有两种互斥的意图：

| 用户的意图 | 怎么做 | 怎么验 |
|---|---|---|
| **下载保持直连**（多数情况） | 什么都不用做，宿主直连已经给了你这个结果 | 下载时查一次连接，确认**没有**经过代理节点 |
| **下载器要走代理** | ⚠️ **不能靠改宿主网关来实现**——那会违反宿主直连的硬约束、触发开机死锁。只能**在容器那一侧显式配代理**（给那个容器单独设代理环境变量或配置项） | 从该容器内部验出口，不是从宿主 |

⚠️ **本手册不提供"让宿主整体走代理"的路径。** 用户如果坚持要那样，
**报告这个冲突**，让用户明白代价是开机死锁风险，而不是默默照做。

### 「全屋，但排除某几台」怎么做

这是最常见的真实需求（想让电视和手机走，又不想动工作机），
而它的做法就是上面那张表的一般化：

1. **先把例外清单列出来**——哪几台不要走，白纸黑字，不要靠记
2. **例外设备改静态**，网关写死主路由；或者在主路由上给它们单独留策略
3. **再改主路由的全屋下发**
4. **顺序不能反**：先下发再去捞例外，中间那段时间它们已经走上旁路由了。
   对工作机来说，这可能就是一次会议掉线

⚠️ **例外清单是要维护的。** 以后家里新加一台设备，它默认落在"走旁路由"那一侧——
这既是这个方案的优点（新设备自动被保护），也是它的坑（新的工作机也会被卷进去）。
**把这张清单和[端口表、落点表](../services/_deployment.md#要自己维护的两张表)放在一起。**

**怎么确认宿主真的锁住了**（★ 在宿主上跑，不是在 VM 里）：

```sh
EXPECT=<主路由 IP>        # ← 先填上，这一步不能省

# Linux
ACTUAL=$(ip -4 route show default | awk '{print $3; exit}')
# macOS
ACTUAL=$(route -n get default 2>/dev/null | awk '/gateway:/{print $2; exit}')

[ -n "$ACTUAL" ] && [ "$ACTUAL" = "$EXPECT" ] \
  && echo "OK：网关是 $ACTUAL" \
  || echo "FAIL：实际是 ${ACTUAL:-（没有默认路由）}，期望 $EXPECT"
```

⚠️ **必须做这个比较，不要只把网关打印出来看。**
`route -n get default | grep gateway` 这种写法**只要存在任意默认网关就会退出 0**——
哪怕它正指着那台 VM，命令也"成功"。一条无论如何都会通过的检查，比没有检查更危险。

⚠️ **什么时候跑**：要在主路由改完下发**之后**，而且宿主已经重新拿过一次网络配置。
分两种情况，别混：

| 宿主的配置方式 | 怎么让它重新取一次 |
|---|---|
| **已经改成静态**（推荐做法） | 它本来就不吃 DHCP，**没有租约可续**。断网重连一次或重启，确认静态配置生效即可 |
| **还在吃 DHCP**（尚未改静态） | 等它续租，或手工触发一次续租 / 重连，让新下发的网关落到它头上 |

改之前跑这条必然通过，证明不了任何事。

## 回滚路径

动手前必须确认：**到旁路由的管理通道是局域网直连、不经代理。**

否则代理配坏 → SSH 也走代理 → 进不去 → 无法回滚，只能物理接触机器。

全屋异常时的回滚顺序：

1. 主路由上把下发的网关/DNS 改回主路由自己
2. 已经手动指过网关的设备，改回自动获取
3. **让客户端真正重新取一次配置**——见下面那条，这一步最容易以为做了其实没做
4. 确认恢复后，再回头查旁路由

⚠️ **第 1 步不会自动生效。改回下发 ≠ 客户端已经改回来。**

客户端手上那张租约是有期限的（家用路由器常见 12 或 24 小时），
**在它到期之前，那台设备的默认网关仍然指着已经坏掉的旁路由。**
症状很难受：你在主路由上明明改回去了，一部分设备恢复了，
另一部分还是不通——**而两者的配置看起来完全一样。**

所以第 3 步要逐类做，别只做一台：

| 设备 | 怎么让它重新取 |
|---|---|
| Windows | `ipconfig /release && ipconfig /renew` |
| macOS / Linux | 关掉再打开网络接口，或重连 Wi-Fi |
| 手机 / 平板 | 关掉 Wi-Fi 再连，或开关一次飞行模式 |
| 电视 / 游戏机 / IoT | 多半只能**重启设备**——这些东西通常没有释放租约的入口 |

📌 **回滚前就该知道自己家的租约期是多久。** 在主路由的 DHCP 设置里看得到。
期限很长（超过几小时）的话，**回滚计划里必须包含"逐台重连"这一步的时间成本**，
不能假设改完就好。

**回滚要能在不碰旁路由的情况下完成**——因为出问题时你可能正好连不上它。

## 验收

```yaml
verify: |
  # 在一台【客户端】上执行，网关已指向旁路由
  # 1. 基本连通：能不能出网
  curl -s -o /dev/null -w '%{http_code}\n' http://<某个国内站点>
  # 期望: 200 或 204

  # 2. 关键：确认没有拿到旁路由发的 DHCP
  #    客户端的 DHCP 服务器地址应当仍是主路由 192.0.2.1
  #    Linux (NetworkManager): nmcli -f DHCP4.OPTION device show <网卡> \
  #                             | grep dhcp_server_identifier
  #    Linux (systemd-networkd): networkctl status <网卡> | grep -i 'DHCP4 Server'
  #    macOS:                    ipconfig getpacket en0 | grep server_identifier
  #    ⚠️ 查不到就直接看客户端拿到的租约文件，别用日志grep——
  #       日志可能是历史记录，不代表当前租约
  # 期望: 192.0.2.1（主路由），不是旁路由的地址
```

**第 2 条不能省。** 旁路由的 DHCP 没关干净，短期内可能什么都不发生
（主路由抢先回应），几天后才随机爆发。

⚠️ 不要用"在旁路由上自测能出网"代替这个验收。见
[`services/_schema.md` 的 `verify` 说明](../services/_schema.md#verify--最重要的字段)。
