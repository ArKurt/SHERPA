# 冷启动验收

> 一份清单。配完开机自恢复之后**真的断电重启一次**，逐项走完。
>
> **不重启验证的自启动配置，等于没配。**

## 什么时候做

- 配完 [`boot-persistence.md`](boot-persistence.md) 之后
- 每次改动启动链之后
- 系统大版本升级之后
- **搬家、换电源、换 UPS 之后**

## 动手前：这一步要不要先问人

**冷启动验收本身是必要的**，但它在某些形态下**不是一次普通验收，
而是主动制造一次全屋故障**。

先回答一个问题：**这台机器身上有没有别人依赖的职责？**

| 这台机器 | 断电意味着 | |
|---|---|---|
| 只跑你自己用的服务 | 你自己不方便一会儿 | 直接做 |
| **是全屋的网关 / 旁路由** | **全家断网**，包括不在乎这些服务的人 | ⚠️ **停下来问人** |
| **是 NAS，还跑着别人在用的服务** | 下载中断、正在看的片停了 | ⚠️ **停下来问人** |
| 跑着自动化、监控、常驻 agent | 那段时间它们全都不在 | ⚠️ **停下来问人** |

⚠️ **`risk: high` · `needs_human`** —— 命中上面任何一条时，
**必须先取得一个停机窗口的授权**，说明清楚：会断多久、期间什么不能用、
以及万一起不来的补救方式。

**"我有办法修"不等于"现在可以断"。** 前者是可恢复性，后者是授权。

> 💡 **能避开就避开**：把这次验收安排在**全屋切换之前**做——
> 那时这台机器还没有承担全屋职责，断电只影响你自己。
> 一旦切过去了，再想验收就得申请停机窗口。
> → [层 2 · 推进顺序](../layers/2-gateway.md#推进顺序关键)

## 怎么做

**真的断电**，不是软重启。软重启保留了很多状态（挂载、已解锁的加密卷），
测不出真实的冷启动行为。

⚠️ 断电前先确认：**如果它起不来，你有办法进去修。**
物理接触得到机器，或者有另一条不依赖它的网络路径。

## 清单

### 阶段 0 · 加电后、无人干预

- [ ] 机器通电自动开机（还是需要按电源键？）
- [ ] 如果开了全盘加密：**先按 [`ops/boot-persistence.md`](boot-persistence.md#全盘加密会限制自恢复能力)
      确认这套加密停在哪一步**——是停在解锁界面等人，还是 TPM 自动过了，
      还是可以远程解锁。**三种都存在，不要默认它一定会停。**
      把它实际的行为记下来当基线，并记下"此刻有哪些东西不可用"

### 阶段 1 · 登录、解锁后

> 📌 **macOS 上这一阶段是一条链，不是一步。** 少数清楚这一点的人才验得对：
>
> ```
> 通电 → ①解锁（若开了 FileVault）→ ②容器运行时起来 → ③容器起来
> ```
>
> **②不是自动的，而"怎么才算自动"取决于你用哪个运行时——别按"桌面应用"一概而论：**
>
> | 运行时 | 无人值守能不能起来 |
> |---|---|
> | **OrbStack** | ✅ 官方明确支持**完全不用 GUI**，场景直接包括 headless server（`orb start`） |
> | **Docker Desktop** | ❓ **本手册未验证。** 它的设置项写的是"登录时启动"，同时又有 `docker desktop start` 这个 CLI——**没有图形登录时能不能起来，我们没有实测，也没找到官方保证** |
>
> **所以第 ② 步要写下来：这台机器上的运行时，是靠什么起来的。**
> 不确定就当它起不来，先验一次再承诺。
>
> ⚠️ **这条链会制造假通过，判据是这一句**：
> **任何在你介入之后才正常的检查，都不算数。**
>
> 所以阶段 1 的正确做法是：**先在没有任何人登录（图形或 SSH）的状态下，
> 从另一台机器看一眼容器在不在**——那才是"它会自己回来"的证据。
> 你登录之后、或者你自己动手把运行时拉起来之后看到的"都在"，证明不了任何事。
>
> 两条最常见的假通过路径：
> - 这台机器上**本来就有一个活着的图形会话**（开了自动登录，或者有人"顺手登一下看看"）
> - 你 SSH 进去之后**自己把运行时起了**，然后检查容器
>
> 这和[坑典里"登录一次就都正常"](../pitfalls/boot-ops.md#重启后服务没回来但登录后一看又都正常)
> 是同一个陷阱。
>
> **这是选型问题，不是配置问题**——要在装之前决定，
> 而不是断电之后才发现运行时需要有人来点一下。

- [ ] 容器运行时启动
- [ ] 所有容器按重启策略回来了
- [ ] 原生服务回来了
- [ ] **虚拟机回来了**，且**只有一个实例**
      （`ps` 确认没有两个虚拟机进程抢同一块磁盘）

### 阶段 2 · 存储

- [ ] 所有外接盘/网络挂载都挂上了
- [ ] 挂载点路径和之前一致（有些系统会加 `-1` 后缀）
- [ ] **服务看到的是真实数据，不是空目录**
      —— 这条最重要。挂载晚于服务启动时，服务可能已经在空目录上初始化过了

### 阶段 3 · 网络

- [ ] 旁路由的 IP 是预期的那个
- [ ] 旁路由的 DHCP 服务**是关的**
- [ ] 从一台**客户端**测：能出网、且走的是预期出口
- [ ] 组网工具重新连上了
- [ ] **路由表里没有指向不存在设备的残留条目**
      → [坑典 · 幽灵路由](../pitfalls/boot-ops.md#幽灵路由退役设备留下的影子)

### 阶段 4 · 入口（如果有）

- [ ] 隧道客户端重连成功
- [ ] **从外网**访问一个服务，返回预期状态
- [ ] 证书有效，自动续签任务在跑

### 阶段 5 · 应用

- [ ] 逐个服务跑它自己的 `verify`（**从客户端**）
- [ ] 定时任务回来了（备份、清理、DNS 更新）

## 记录结果

把"哪些需要人工干预才能恢复"记下来。**这份清单本身就是价值**——
下次真的断电时，你知道该做什么，而不是从零排查。

特别记下：

- 冷启动到完全可用需要多久
- 哪些步骤必须有人在场
- 哪些服务的恢复有先后依赖

## 如果有些东西没回来

不要现场手工拉起来就算完——**那只是掩盖问题**。
找到为什么没自启，修好，再冷启动一次验证。
