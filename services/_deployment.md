# 服务怎么摆

> 每个服务模块的 `rollback` 都写着 `docker compose down`，
> 但没说 compose 文件放哪、装到第六个服务时怎么才不乱。这一页补上。
>
> **这里给的是一种够用的组织方式，不是唯一正确答案。** 关键是**一致**——
> 六个月后的你（或者接手的人）能一眼看出东西在哪。

## 一个原则

**配置和数据分开放，且分别对应不同的备份策略。**

```
配置   小、要进版本管理、不含凭证        → 内置盘，备份代价近乎为零
凭证   小、绝不进版本管理                → 见 ops/secrets.md
数据   大、不进版本管理、决定备份成本    → 落点见层 5
```

这三样混在一个目录里，你就没法回答"我该备份什么"——
而这个问题必须在灌真实数据之前回答。

## 一种够用的布局

```
~/services/
├── .gitignore              # 忽略 .env 与任何数据目录
├── jellyfin/
│   ├── compose.yaml
│   ├── .env                # ⚠️ 不进版本库
│   └── config/             # 该服务的配置与元数据库
├── immich/
│   ├── compose.yaml
│   ├── .env
│   └── config/
└── ...

/data/                      # 体积数据，落点由层 5 决定
├── photos/
└── media/
```

**一个服务一个目录、一个 compose 文件。** 不要把十个服务塞进一个大文件——

| | 一服务一文件 | 全塞一个文件 |
|---|---|---|
| 单独重启一个服务 | ✅ | ⚠️ 容易误伤 |
| 单独升级 / 回滚 | ✅ | ❌ 牵一发动全身 |
| 出错时定位 | ✅ 影响面清楚 | ❌ 一处语法错，全部起不来 |
| 端口冲突 | 要自己留心 | 相对好查 |

最后一条是全塞一个文件的唯一优势，而它可以用一张端口表解决（见下）。

## 要自己维护的两张表

手册管不到你的现场，这两张表只能你自己记——**记在你的工作笔记里，不是本仓库**：

**① 端口表** —— 谁占了哪个端口。装到第六个服务时，没有这张表必然撞车，
而撞车的症状是"容器起不来"，报错未必指向端口。

**② 落点表** —— 每个服务的配置在哪、数据在哪、备份到哪。
这张表就是你的备份清单，也是迁移时的搬运清单。
→ [`../ops/backup.md`](../ops/backup.md)、[`../ops/migration-retirement.md`](../ops/migration-retirement.md)

## 版本

**不要用 `latest`。** 写死具体版本号。

- `latest` 意味着**任何一次重启都可能是一次升级**，而你不知道它升了什么
- 出问题时你无法回到"刚才那个能用的版本"
- **有依赖关系的组件必须钉同一个版本**（典型：相册的主服务与机器学习服务）

升级是有意的动作：改版本号 → 读上游的 release notes → 确认有备份 → 升。

## 一次装一个

**装一个，按它的 `verify` 验收通过，再装下一个。**

同时装五个服务出了问题，你分不清是谁的错——而它们会互相干扰
（端口、卷权限、资源争抢），让排查难度不是相加而是相乘。
