# 多人共用与交接

> 这一章处理手册其它地方没有的一个维度：**人**。
>
> 前面所有章节都是设备视角——哪台机器、哪块盘、哪条链路。
> 但一台服务器只要不止一个人用，就会出现设备视角看不见的问题。
>
> ⚠️ **只有你自己用的话，这一章可以跳过。**

## 什么时候需要读这一章

| 情况 | |
|---|---|
| 只有我自己用 | 跳过 |
| 家里人也用（伴侣、孩子、父母） | 读「单点故障的社会成本」和「最低限度的交接」 |
| **工作室 / 微型企业** | **整章都要读。断网即停工，而且迟早要换人** |

---

## 一、单点故障的社会成本

技术上的单点故障，手册前面讲过很多。**这里讲的是它的另一面：故障发生时，
受影响的不只是你。**

### 一台机器扛的东西越多，停机的代价越大

装完之后，回答一个问题：**这台机器停一小时，谁会受影响？**

| 它承担的职责 | 停机时谁疼 |
|---|---|
| 只放你的媒体库 | 你自己 |
| 全屋网关 / 旁路由 | **所有人，包括不用这些服务的人** |
| **局域网 DNS** | ⚠️ **所有人，而且症状是"整个网络坏了"** |
| 共享素材库 | 所有正在用它工作的人 |
| 公网入口 | 所有从外面访问的人 |

⚠️ **局域网 DNS 这条特别值得单独说。**

把 [层 7](../layers/7-lan-addressing.md) 的局域网 DNS 架在这台服务器上很方便——
但它一重启，**所有指向它的设备都会解析失败**。对用户来说，症状不是
"素材库打不开"，而是"**网断了**"，因为浏览器打开任何网站都在等 DNS 超时。

维护窗口因此从"重启一下服务器"变成"通知所有人"。

**降低办法**：主路由上配一个**备用 DNS**，指向公共 DNS 或主路由自己。
这样服务器 DNS 挂掉时，内网域名解析不了，但**上网不受影响**——
故障面从"全断"缩小到"内网服务暂时用不了"。

### 停机窗口要提前约

工作室场景下，下列操作**都需要提前约时间**，不能想做就做：

- 冷启动验收（[`cold-start-acceptance.md`](cold-start-acceptance.md) 已有这条门）
- 切换全屋网关 / 改主路由下发
- 存储迁移、盘更换
- 大版本升级

**"我有办法修"不等于"现在可以停"。**

## 二、多人共用：三件事要先想清楚

### 其一：每个服务有自己的账号体系

手册收录的服务**没有统一登录**。装了六个服务，就是六套账号。

这带来的实际问题：

- 加一个人要在六个地方各建一次账号
- **走一个人要在六个地方各删一次**——漏掉一个就是长期的越权访问
- 密码策略无法统一

⚠️ **手册不覆盖单点登录（SSO）方案。** 那是另一个量级的复杂度，
而且做错了会把"六个各自独立的服务"变成"一个挂了全挂的服务"。
人少的时候，**一张记录"谁在哪些服务上有账号"的表更实用**。

### 其二：区分"用服务"和"改配置"

这两种权限完全不同，但很容易混：

| | 用服务 | 改配置 |
|---|---|---|
| 谁需要 | 所有人 | **尽量少的人** |
| 出错后果 | 影响自己 | **影响所有人** |
| 手册里对应 | 各服务自己的账号 | SSH、容器运行时、主路由、旁路由 |

⚠️ **不要因为"方便"把服务器的 SSH 密钥发给每个人。**
一个人误操作，全工作室停工——而且事后查不出是谁。

### 其三：共享数据要先说清楚"谁能删"

共享素材库最常见的事故不是硬件坏，是**有人删了别人还在用的东西**。

- 用同步类工具（如 [Syncthing](../services/syncthing.md)）时尤其危险——
  **它同步的是状态，一端删了另一端也会删**
- 上线前**开启版本控制**，那是唯一的后悔药
- **明确告诉所有人：这是同步，不是备份**

→ [坑典](../pitfalls/services.md#syncthing-把文件双向删了)

## 三、交接：换人时要交出什么

**这一节的前提是一件容易被忽略的事**：手册要求你维护的两张表
（端口表、落点表，见 [`../services/_deployment.md`](../services/_deployment.md#要自己维护的两张表)）
**被明确要求放在仓库之外**——因为它们含现场信息。

所以它们**不会跟着仓库一起交接**。你得单独处理。

### 一份能交接的记录，至少包含

- [ ] **端口表** —— 谁占了哪个端口
- [ ] **落点表** —— 每个服务的配置在哪、数据在哪、备份到哪
- [ ] **装机清单** —— 当初向导生成的那份，说明"为什么是这套架构"
- [ ] **改过手册默认做法的地方** —— 以及为什么改
- [ ] **主路由上做过什么** —— 静态绑定、DHCP 保留、端口转发、下发的网关/DNS
- [ ] **各服务的管理员账号在谁手里**
- [ ] **凭证的位置**（不是凭证本身）→ [`secrets.md`](secrets.md)
- [ ] **已知的坑与临时处置** —— "这个我知道，但先这样凑合着"的那些

### 凭证怎么交

⚠️ **不要把凭证贴进聊天、邮件或工单。**

正确做法见 [`secrets.md`](secrets.md#轮换)。核心是两条：

1. 交接**位置和取用方式**，不是凭证本身
2. **交接完成后轮换一遍** —— 前任仍然知道旧的那些

### 判断"接手成功"的标准

**不是"我讲完了"，是接手的人能独立做到这三件事：**

```
1. 从零复现一次冷启动验收 —— 证明他知道系统怎么起来的
2. 独立完成一次备份恢复演练 —— 证明出事时他救得回来
3. 说得出这台机器停一小时谁会受影响 —— 证明他知道风险在哪
```

⚠️ **第 2 条不能省。** 一个不会恢复备份的接手人，等于没有备份。

> 💡 交接的最好时机是**你还在的时候**。让接手的人在你旁边做一次上面三件事，
> 比留一份文档有效得多——文档回答不了他没想到要问的问题。
