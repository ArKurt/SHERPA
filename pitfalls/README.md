## 六条通用规律

认出模式比记住条目有用。这些坑背后是同一批东西：

### 规律一：「A 能通」不等于「B 能通」

- 核能出海 ≠ 客户端能借道
- 终端 curl 通 ≠ 服务进程连得上
- 从睡眠唤醒成功 ≠ 从关机唤醒成功
- Web 界面能开 ≠ 功能可用
- 我的电脑能开 ≠ 电视能开

**验证必须在真实的使用路径上做。** 这就是本手册所有 `verify`
都要求"从客户端跑"的原因。

### 规律二：兜底链路会静默失效

任何"其它情况走 X"的兜底，都要问一句：**X 会漂到哪里去？**
如果它可能漂到一个不可用的地方，故障是必然的，只是时间问题——**而且它不报错**。

### 规律三：总开关

很多配置项**各自带一个默认关闭的总开关**。只填了内容没开开关 = 白填，
而且看起来像"配置语法不对"，会让你查错方向。改完回头确认开关状态。

### 规律四：退役的东西会留下影子

关机 ≠ 清理干净。指向已死设备的残留配置会造成**间歇性、不可复现、
且症状指向别处**的故障。

### 规律五：外部依赖会过期

社区规则集、第三方镜像、非官方分支——**用之前看更新日期和维护活跃度**。
它们不会通知你自己已经过时了。

### 规律六：症状的严重程度和原因的深度无关

最难查的几个坑，症状都很轻微（间歇 502、偶尔掉登录、某个设备发现不了）。
**症状轻不代表原因简单。**

## 这里没有你的问题？

1. 确认你**测的是哪一层** —— 会话环境变量、系统代理、旁路由透明代理是三层不同的东西
2. 回到对应的 [层文档](../layers/) 看该层的验收，确认前置条件都满足
3. 再放大范围检索

**别急着改配置。** 上面几个坑里，至少有三个的第一版诊断是错的——
包括本手册作者自己排查时。**先取证，再动手。**
