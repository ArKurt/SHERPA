# 各服务的坑

> 相关：[`services/`](../services/)
>
> 每条都指向对应的服务页——那里有完整的部署要求。

## Home Assistant 一个设备都发现不了

**症状**：Web 界面完全正常，但自动发现列表是空的，**而且不报错**。

**原因**：用了容器的默认桥接网络。HA 靠 mDNS / SSDP / 广播发现设备，
而**这些广播不会穿过默认桥接**。
（这是社区里一致的经验；HA 官方文档要求 host 网络，但没有解释这个原因。）

**修法**：改用 host 网络模式，或 macvlan，或原生安装。
→ [`services/home-assistant.md`](../services/home-assistant.md)

⚠️ 注意这和[层 2 明确否决的"代理跑 host 网络"](../layers/2-gateway.md)不是一回事：
HA 需要收广播，代理需要独立 IP，需求相反。

## Immich 主服务崩溃重启循环

**症状**：主服务反复重启，机器学习服务看起来正常。

**已知诱因**：**主服务与机器学习服务版本不一致**——用了 `latest`，
或者升级时只改了其中一个。
（手册观察到的那一次就是如此；**官方文档没有记载这个因果**，
所以别把它当成唯一诊断——排查时同时看日志里真正的报错。）

**修法**：两个钉死同一个版本号，升级时一起改。不要用 `latest`。
→ [`services/immich.md`](../services/immich.md)

> 另一个更严重的 Immich 事故（数据库落在会掉线的盘上）见
> [存储的坑](storage.md#数据库和媒体库同盘盘一走就崩溃循环)。

## 密码库客户端登录后无法解锁

**症状**：能登录，但保险库解不开，报错难懂。

**原因**：走的是纯 HTTP。Bitwarden 系客户端依赖浏览器的加密 API，
**只在安全上下文（HTTPS）里可用**。

**修法**：配 HTTPS。内网也要——这正是内网需要域名和证书的典型理由。
→ [`services/vaultwarden.md`](../services/vaultwarden.md) ·
[层 7](../layers/7-lan-addressing.md)

## 面板里点某些服务没反应

**症状**：导航面板上，别的图标都正常，某几个点了完全没反应。

**原因**：那几个用了"内嵌 iframe 打开"模式，而目标服务前面有认证、
或者自己会做重定向。**跨域 iframe + 认证 + 重定向，三者叠加会失效。**

难点在于**症状是"点了没反应"**，看不出是哪一环的问题。
真实案例里排查了一轮才发现内嵌本身就是失败原因，而且中途还误判过。

**修法**：认证类服务和管理界面一律用**新标签页**打开。
→ [`services/sunpanel.md`](../services/sunpanel.md)

## Syncthing 的界面从别的机器打不开

**症状**：服务在跑，从本机能开，**从另一台机器连接被拒绝**。

**原因**：Syncthing 的 GUI **默认只监听 `127.0.0.1`**。

⚠️ 这个坑会给你一个**假失败**——你会去查网络、查防火墙，而问题在配置里。

**修法**：改 `gui.address`，或走容器端口映射 / 反向代理。
→ [`services/syncthing.md`](../services/syncthing.md)

## Syncthing 把文件双向删了

**症状**：一端删了文件，另一端也没了。或者配错方向，一次性删掉大量数据。

**原因**：Syncthing 同步的是**状态**，不是"追加"。它忠实复制你的操作，**包括误删**。

**修法**：上手时先用"仅发送/仅接收"模式确认方向，**开启版本控制**（唯一的后悔药），
先拿测试文件夹跑通。

> **Syncthing 不是备份。** 备份要另做。
→ [`services/syncthing.md`](../services/syncthing.md) · [`ops/backup.md`](../ops/backup.md)

## aria2 的 RPC 裸奔

**症状**：没有症状。但任何能访问到它的人，都能**往这台机器上任意写文件**。

**原因**：aria2 的 RPC 接口**默认没有认证**。

**修法**：必须设 `--rpc-secret`；**绝不要把 RPC 端口转发到公网**。

⚠️ 另外：密钥不要作为**命令行参数**传——同机任何进程 `ps` 一下就能看到。
→ [`services/aria2.md`](../services/aria2.md) · [`ops/secrets.md`](../ops/secrets.md)

## 串流卡顿

**症状**：远程桌面 / 游戏串流延迟高、画面卡。

**原因**：流量走了代理。串流走 UDP、对延迟极其敏感，**绝不能经过代理**。

**修法**：在旁路由上给串流目标加直连规则，或把这台机器排除在旁路由之外。
→ [`services/sunshine-moonlight.md`](../services/sunshine-moonlight.md)

## WoL 从没成功过

**症状**：发了魔术包，机器纹丝不动。

**原因**（按可能性排序）：

1. BIOS/UEFI 里没开网络唤醒
2. 操作系统关机时切断了网卡供电（Windows 的"快速启动"是常见元凶——
   它的"关机"其实是休眠）
3. 发包的机器和目标不在同一个二层网络里（魔术包是广播，**跨不了路由**）
4. 交换机 / AP 丢弃了广播包

⚠️ **一定要在真正关机的状态下测。** 从睡眠唤醒的条件宽松得多，
测睡眠唤醒成功不能证明关机唤醒可用——而你真正需要的往往是后者。

→ [`ops/wol.md`](../ops/wol.md)

## AI CLI 报证书自签，怀疑代理在中间人

**症状**：在某个 AI 工具的会话里 `curl` 它自己的域名，证书验证失败。
看起来像旁路由的透明代理在做中间人。

**原因**：**不是旁路由。** 很多启动 AI CLI 的包装器会给会话注入代理环境变量
（`HTTPS_PROXY`），指向一个本机端口，并用自签证书做中间人。

真实案例里这个现象一度被归因为旁路由，后来剥掉环境变量直连验证，
证书完全有效——**旁路由从头到尾没碰过它**。

**修法**：

```sh
env | grep -i proxy        # 先看会话里有没有被注入
env -u HTTPS_PROXY -u https_proxy -u HTTP_PROXY -u http_proxy \
  curl -sI https://<目标域名> | head -3
```

两者结果不同 → 问题在会话层，不在网络层。

### 教训

> 诊断代理问题时，**先确认你测的是哪一层**。
> 会话环境变量、系统代理设置、旁路由透明代理是三层不同的东西，
> 症状很像但修法完全不同。**搞错了会去改一个根本没问题的组件。**
