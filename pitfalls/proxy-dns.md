# 代理与分流的坑

> 相关层：[层 3 · 代理栈](../layers/3-proxy-stack.md) · [层 4 · 分流与 DNS](../layers/4-routing-dns.md)
>
> 这几个坑的共同点：**症状不指向真凶**，而且组件自测全是绿的。

## 裸核模式：核能出海，客户端全断

### 症状

- 插件面板显示运行中 ✅
- 在**路由器上**测代理端口，能出海，返回 204 ✅
- **客户端把网关指过来，国内外全断** ❌
- 严重时连路由器管理界面都像打不开

### 原因

有的代理插件有一个"**只启动内核**"的模式（不同插件叫法不同：裸核、core only、仅内核）。
原型阶段单机验证内核时它很方便，切到旁路由时**极容易忘记关掉**。

**手册撞上的是 Nikki 的这个开关**：打开时插件只当内核的启动器，
**它的混入配置和代理集成不生效**——没有插件提供的控制接口、没有它配的透明代理入口、
它那套流量劫持规则一条都没写进防火墙。

于是客户端的流量既不被透明代理接管，又在单臂发夹转发时撞上防火墙的转发拒绝规则，
**两条路都断**。

> ⚠️ **别把这条读成"裸核 = 什么都没有"。** 如果你是有意让内核自己用 TUN / auto-route
> 接管，那条路是成立的——Nikki 维护者的讨论里就把它当作有效对照。
> 失效的是**插件那套集成**，不是"所有劫持"。
> 其它插件有没有同类开关、开了之后停掉什么，**按各自文档核**。

### 修法

关掉裸核模式，然后**逐项确认集成件都在**（只确认"服务已重启"不够）：

- [ ] 对外控制接口在监听
- [ ] 透明代理端口（重定向 / tproxy）在监听
- [ ] tun 设备已创建并 UP（如果用 tun 模式）
- [ ] 防火墙里有劫持规则，且**数量不为零**
- [ ] 策略路由规则存在

### 教训

> **「核能出海」≠「客户端能借道」。**

这条是本手册**所有 `verify` 字段都要求从客户端视角写**的直接来源。
agent 比人更容易停在"自测通过"就宣布完成。

## fake-ip 三连

> ⚠️ **先确认你在 fake-ip 模式。** mihomo 的 `enhanced-mode` **默认是 `redir-host`**，
> 不是 fake-ip——是插件预置和机场订阅经常把它打开。
> 不在这个模式的话，下面三个都跟你无关。判定方法见
> [层 4](../layers/4-routing-dns.md#先确认你到底是不是-fake-ip-模式)。

启用 fake-ip 之后：DNS 不做真实解析，返回 `fake-ip-range` 里的一个假地址
（常见是 `198.18.0.0/15`，**但以你自己配置里那行为准**），
等流量真发出来时代理再按域名建连接。

这么做是为了**让代理拿到域名**——否则客户端先解析出真实 IP 再连，按域名写的规则全失效。

代价是：**任何"拿到 IP 后自己去连"的东西都会拿到假地址。** 下面三个都是这个代价的变体。

### 之一 · 局域网服务访问不了

**症状**：局域网里用主机名访问自己的服务（`http://myserver:8080`）失败，
用 IP 访问正常。反代场景下常表现为 502。

**原因**：裸主机名被送进了代理的 DNS，而它既没被本地解析接住、也不在 fake-ip 过滤列表里，
于是拿到了一个 fake-ip 映射地址。客户端拿着那个地址去连——那里什么都没有。

⚠️ **先用一次 DNS 查询确认真是这个因果**（看返回的地址在不在你的 `fake-ip-range` 里），
别把所有"用主机名连不上"都归到这一条。

**修法**（按可靠性排序）：

1. **在 fake-ip 过滤列表里加上内网用的后缀**，让它们走真实解析。
   ⚠️ **这里有两类不同的东西，别混：**

   | 后缀 | 为什么加进过滤列表 | 能不能拿来当 LAN DNS 后缀 |
   |---|---|---|
   | `.local` | 保护**合法的 mDNS**不被代理劫持 | ❌ **不能。** 它是 mDNS 保留后缀 |
   | 你的内网 DNS 后缀 | 让内网域名解析到真实 IP | ✅ 就是它 |

   **加进过滤列表 ≠ 可以拿它当普通 DNS 后缀。**
   内网该用什么后缀，判据见 [层 7](../layers/7-lan-addressing.md#用什么后缀)——
   `.local` 在那里是明确禁项。

2. **给内网服务配真实的内网域名**（不是裸主机名，也不是 `.local`），配合上一条
3. **客户端 hosts 硬编** —— 最快，但每台设备都要做。当止血用，别当方案

⚠️ **自定义之前，先看清这个数组是"追加"还是"整表替换"**——两种语义都存在，
按你手上这个插件的实现来。替换语义下，你一自定义，插件内置的那些条目
（常见的游戏机域名等）就全不生效了，要一并补齐。
**改之前在临时副本上看一眼合并后的最终数组**，比事后排查便宜得多。

→ 内网该怎么起名字，见 [层 7](../layers/7-lan-addressing.md)

### 之二 · 组网工具的域名被吃掉

**症状**：装了 Tailscale / ZeroTier 一类的组网工具，**用它们的 IP 能连，用名字连不上**。

**原因**：同上，`*.ts.net` 这类名字被拦下给了 fake-ip。

这种情况下**路由层往往本来就是对的**——如果代理侧已经把 `100.64.0.0/10`
和 `fc00::/7` 直连、不劫持，坏的就只有名字解析这一层。
所以症状是"IP 能通、名字不通"，很容易误判成组网工具本身的问题。

⚠️ **但别假定它默认就直连了。** 这两段在不在直连列表里、要不要额外加 fake-ip 过滤、
相关开关默认开还是关，**都要从最终生效的配置里确认**。

**修法**（两件事都要做，缺一不可）：

1. **DNS 策略**：把 `*.ts.net` 这类后缀指向组网工具自己的 DNS 服务器
   （Tailscale 的 MagicDNS 是 `100.100.100.100`，IPv6 是 `fd7a:115c:a1e0::53`）
2. **fake-ip 过滤**：把同样的后缀加进过滤列表，否则策略解析出真实 IP 后还是会被换成假的

⚠️ 这两项**各自可能还有一个总开关，而开关的默认值别猜**——
只填了列表没开开关 = 白填。逐项去读当前生效的配置。

⚠️ **把设备的网关切到旁路由之前，先解决这个。** 否则组网工具会在切换的瞬间失联，
而你可能正靠它远程管理这台设备。

### 之三 · 两套 DNS 劫持打架

**症状**：DNS 解析结果随机、时对时错，重启后表现又变了。

**原因**：路由系统自带的 DNS 服务（dnsmasq 一类）常有个"DNS 重定向"选项，
把客户端的查询劫持到自己这里；而代理插件也在做同样的事。
**两套劫持同时开，谁生效取决于防火墙规则的顺序**，结果不可预测。

**修法**：关掉路由系统自带的那个，让代理插件独占 DNS 劫持。
**Nikki 的官方文档明写要求关掉 OpenWrt 的 DNS 重定向**，否则可能导致污染或分流错误。
其它插件按各自文档核——这条常常不在安装步骤里，容易漏。

## 兜底链路把服务静默杀死

### 症状

**没有任何配置变更**，某个服务某天开始不可用。可能表现为"用着用着掉登录"，
而不是干脆连不上。过几天又自己好了。

### 原因

订阅的兜底规则通常是"其它所有流量 → 某个自动选择组"。
**这个组按什么挑节点，要看它是哪种类型**——按延迟测速挑的话，选中的常常是
离你最近的地区。**先读你自己那个组的类型和策略**，别假定都是按延迟。

如果某个服务在自动组可能落到的地区不可用，组一漂过去，服务立刻失效。
触发条件是**网络延迟的自然波动**，所以它不可复现、也不报错。

已知实例（2026-08-28 核对）：**Anthropic 与 OpenAI 的官方支持地区清单都不含香港**——
官方措辞是"不在支持范围"，不是"屏蔽"，但落到那儿的效果一样。各家流媒体同理。
手册撞上这条，是在 2026-08-27 的一套 Nikki/mihomo 配置上，兜底 Auto 漂到了香港。
**这些清单会变，用之前自己去看当天的官方页面。**

### 修法

给这类服务**单独建组、手工指定地区，组里不放自动选项、不放被屏蔽的地区**，
并把规则放在规则表最前面。

具体配法见 [层 4 · 地区敏感服务](../layers/4-routing-dns.md)。

### 教训

> 任何"其它情况走 X"的兜底，都要问一句：**X 会漂到哪里去？**

## 同一个站点时好时坏（IPv6 绕过）

### 症状

某个站点，有时走代理、有时直连；换个时间又不一样。
在同一台客户端上，**同一条命令两次结果不同**。

### 原因

客户端同时有 IPv4 和 IPv6 两条出网路径，而代理**可能只接管了 IPv4**
（先按[层 3](../layers/3-proxy-stack.md#ipv6全屋代理绕不开的一问) 实测确认这一点，
别假定）。访问双栈站点时系统可能优先走 IPv6，**直接出网，绕过整个旁路由**。

走哪一族取决于当时的解析结果和系统偏好，所以它**不稳定复现**——
而且症状完全不指向 IPv6。

⚠️ "同一条命令两次结果不同"是这个坑的**可能表现，不是协议保证的行为**。
别反过来用——两次结果相同不能证明没有这个问题，要用下面 `-4`/`-6` 分族去测。

### 怎么确认

```sh
curl -s -4 <回显出口 IP 的服务>
curl -s -6 <回显出口 IP 的服务>
# 两者出口不同 → 就是它
```

### 修法

三种处理方式（关掉 IPv6 下发 / 让代理也接管 / 明确放行并告知用户），
判据见 [层 3 · IPv6](../layers/3-proxy-stack.md#ipv6全屋代理绕不开的一问)。

### 教训

> **"全屋代理"只测了一个协议族，就不叫全屋。**
> 验收要**两族分别证明**。

## 社区规则集过期，漏掉关键域名

### 症状

某个服务**用着用着掉登录**，而不是连不上。重新登录后又能用一阵。

### 原因

现成的规则集很方便，但会过期。**2026-08-27 核对时**看到的一例：某广泛使用的规则集里，
Claude 相关只有 **3 条**、页面标注的最后更新是 **2025-06-06**，
**没有覆盖官方说明里承载 OAuth 令牌刷新的 `platform.claude.com`**。

漏这类域名尤其阴险——它不影响建立连接，只影响**续期**，
所以**预期的症状**是"用一阵就掉"，几乎不可能联想到分流上。

> 📌 说清楚一点：**这次核对确认的是"清单缺了那个域名"，不是"已经复现了掉登录"。**
> 掉登录是按官方端点用途推出来的风险，写在这里是让你知道该往哪儿看。

### 修法

**域名条目少**的服务，直接照官方当前的网络要求写死后缀，
并**记下核对日期、定期回去看**——别假设它一年不变。
也注意官方某一个页面的清单未必覆盖全部产品面（Web / API / 桌面端 / CLI 可能各有各的）。

找官方 allowlist 的关键词：`<服务名> network configuration` / `firewall allowlist`
/ `allowed domains`。

### 教训

> 社区规则集**用之前看两件事：最后更新日期、条目数**。
> 引入一个会过期的外部依赖，比自己写死几条后缀更不可靠。

## 并装了两套透明代理

### 症状

**每个组件单独看都正常**，客户端却不对。手册见过的一种是：
两个插件的面板都显示运行中，但客户端连不上任何东西。
你也可能撞上时好时坏，或只有一部分流量走错——**具体症状取决于两个栈怎么实现**。

### 原因

两套都要管策略路由、防火墙和透明代理入口，**规则的所有权重叠**：
谁最后写谁生效，而它们各自都以为自己说了算。
流量被 A 劫走、按 B 的规则处理，或者反过来。

### 修法

**只装一套。** 想换栈就先彻底卸掉旧的（包括它写进防火墙的规则和开机自启），
确认防火墙干净，再装新的。

这条在手册里是 `conflicts` 硬约束，不是建议。→ [层 3](../layers/3-proxy-stack.md)
