# 层 7 · 内网寻址

> 服务装好了，**怎么访问它？**
>
> ⚠️ **这一层所有人都要读**，和层 2/3/4/6 不同——那几层可以整片跳过，这一层不行。
> 只要你装了任何一个要被别的设备访问的服务，就得回答这个问题。

## 为什么"记 IP"撑不住

起步时用 `http://192.0.2.10:8096` 完全没问题。但它会在四个地方崩掉：

| 什么时候 | 发生什么 |
|---|---|
| 装到第五个服务 | 你要记五个端口号，家里人一个都记不住 |
| 服务器 IP 变了 | 每台设备、每个 App 里填的地址**全部失效** |
| 想上 HTTPS | 证书**签不给 IP 地址**（自签除外，而自签浏览器会拦） |
| 换机器 / 迁移 | 所有客户端都要重配一遍 |

第三条是硬的：**有些服务不上 HTTPS 就不能正常工作**——
比如密码库的客户端需要安全上下文才能解锁
（[`services/vaultwarden.md`](../services/vaultwarden.md#必须是-https)）。
这类服务会直接把你推向"必须有域名"。

## 枚举

| 值 | 做法 | 何时用 |
|---|---|---|
| `ip-static` | 主路由绑定固定 IP，客户端记 `IP:端口` | **起步默认**，一两个服务够用 |
| `hosts-file` | 每台客户端手工写 hosts | 止血用，别当方案 |
| `mdns` | `主机名.local` 自动发现 | 顺带能用，但**覆盖不全** |
| `lan-dns` | 局域网 DNS 给内网域名解析 | **服务多起来之后的正解** |

四种可以叠加，所以 `addressing` 是多值字段。

---

## `ip-static` · 固定 IP

**先做这个，它是其它三种的地基。** 服务器的地址不稳定，后面配什么都是白搭。

做法见 [层 2 · 静态 IP 怎么来](2-gateway.md#静态-ip-怎么来)——
那一节对"服务器主机"和"旁路由"同样适用。

> ⚠️ **不做旁路由的人也要做这一步。** 很容易漏，因为静态 IP 通常被当成"旁路由的需求"。

---

## `hosts-file` · 客户端硬编

在每台客户端的 hosts 文件里写死"名字 → IP"。

- ✅ 立刻生效，不依赖任何服务
- ❌ **每台设备都要做一遍**，手机和电视基本做不了
- ❌ IP 变了要挨个改

**当止血手段用**：某台机器解析出问题、你要立刻恢复访问时，它最快。
**别当方案**——设备数一多就是维护灾难。

⚠️ 硬编过的条目**退役设备时要记得清**，否则会留下指向不存在设备的解析。
→ [`ops/migration-retirement.md`](../ops/migration-retirement.md)

---

## `mdns` · `.local` 自动发现

macOS 和多数 Linux 桌面开箱支持，不用配任何东西，`主机名.local` 就能访问。

**但不要指望它覆盖全部设备**：

| 平台 | 支持 |
|---|---|
| macOS / iOS | ✅ 原生 |
| Linux 桌面 | ✅ 通常装了 Avahi |
| Windows | ⚠️ 较新版本支持，旧版要装 Bonjour |
| Android | ⚠️ 报告称系统层支持不完整，很多 App 解析不了 |
| 电视 / 机顶盒 | ⚠️ 大多报告为不支持 |

> 📌 **这张表是社区普遍报告，不是厂商声明**，各家固件差异很大。
> **拿你自己手上那台设备实测一次**再决定要不要依赖 mDNS——一条 ping 就够。

⚠️ **`.local` 是 mDNS 保留后缀（RFC 6762）。绝对不要拿它当普通 DNS 后缀用。**

RFC 6762 §3 要求：`.local.` 的查询 **MUST** 发到 mDNS 组播地址。
**但紧接着的一句同样重要**——实现 **MAY** 同时并发地去问单播 DNS 并合并结果。

**所以问题不是"你的 DNS 收不到"，而是"两套命名语义压在同一个后缀上"**：
到底哪个答案胜出，取决于这台设备怎么实现、以及当时谁先回。
**结果随设备和时序变化，不可预测。**

这正是它最难诊断的地方——症状是"有的设备能解析、有的不能""同一台机器时好时坏"，
而你会以为是某台设备不守规范。**不是不守规范，是这个后缀本来就有两个主人。**

**结论**：`mdns` 是白拿的便利，不是可依赖的方案。**别把它当成 `lan-dns` 的替代。**

## `lan-dns` · 局域网 DNS

给内网服务一套域名，由局域网里的 DNS 负责解析。**服务多起来之后这是正解。**

- ✅ **一处改，全屋生效**——IP 变了只改一条记录
- ✅ 所有设备都吃（DNS 是最通用的机制，电视也认）
- ✅ 配合反向代理，可以做到"一个域名一个服务"，不用记端口
- ✅ **能签真证书**（见下），于是内网也能上 HTTPS

### 用什么后缀

这是个真判据，选错了要返工：

| 后缀 | 评价 |
|---|---|
| **你拥有的真实域名的子域**（`home.example.com`） | ✅ **推荐**。能签真证书，永远不会和公网冲突 |
| `home.arpa` | ✅ RFC 8375 专为家庭网络保留。**签不了公开信任的证书**，也不能用公共 DNS 根信任链做 DNSSEC 验证（这条是 RFC 8375 明列的边界） |
| `.internal` | ✅ ICANN 董事会决议 2024.07.29.06 已把它**永久保留、不在根区委派**，供私有使用。同样签不了公开信任的证书 |
| `.local` | ❌ **mDNS 保留**，配了也不会生效（见上） |
| `.lan` / `.home` / 自己编的 | ⚠️ 没有正式保留，将来可能被注册成真 TLD 而冲突 |
| 你**不拥有**的真实域名 | ❌ 会劫持真实站点，且无法解释的故障 |

> **有域名就用自己域名的子域。** 这是唯一能同时满足"不冲突"和"能签证书"的选项，
> 而且域名本身很便宜。没有域名就用 `home.arpa`。

### 证书怎么来

内网 IP 签不了公开证书，但**用你自己域名的子域可以**——
通过 DNS 验证方式签发，不需要这台机器暴露在公网上。

⚠️ **证书是对那个域名有效的，不是对 IP 有效。** 证书验证的是域名所有权，
所以只要你的内网 DNS 把这个域名解析到内网 IP，浏览器走域名访问就是绿锁。

**但直接敲 IP 访问不受这张证书覆盖**——那会报证书不匹配。
所以内网也要**一律走域名**，别图省事记 IP。

具体做法看你用的反代与证书工具的文档。→ [层 6](6-ingress.md#反向代理与证书)

### 在哪跑这个 DNS

按省事程度：

1. **主路由自带的静态 DNS 记录** —— 很多路由器支持，零额外维护。**先看有没有**
2. **专门的局域网 DNS 服务** —— 功能全，但多一个要维护的常驻服务
3. **旁路由上的 DNS**（如果你有旁路由）—— 顺手，但**把内网寻址绑在了旁路由的可用性上**

⚠️ 第 3 种要想清楚：旁路由挂了，不只是没代理，**连内网服务的名字都解析不了**。
把两个故障绑在一起会让排查变难。

### 客户端怎么知道要用它

**架起来只是一半。** 客户端不会自己发现这台 DNS——得有人告诉它们。
只有两条路，而且都绕不开主路由：

| 做法 | 说明 |
|---|---|
| **主路由的 DHCP 下发 DNS 地址**（推荐） | 一处改，全屋生效。**这是改主路由的 DHCP 选项，属于铁律①的范围——告诉用户怎么做，不要代劳** |
| 逐台手动填 DNS | 不用动主路由，但每台都要做，且新设备默认不生效 |

⚠️ **这和下发网关是同一个机制，所以同样的三个坑一起来**：

1. **主路由改不改得了？** 有些运营商光猫锁了 DNS 选项——
   锁了就只能逐台手填。**先确认，别做到一半才发现**
2. **想排除某几台？** 同样要先列例外清单，例外设备手动填别的 DNS
3. **改完不会立刻生效**——客户端要等租约续期或重连才会拿到新的 DNS。
   排查"改了没用"之前，先让那台设备重新取一次配置。
   详见[层 2 的回滚一节](2-gateway.md#回滚路径)，那里的租约问题在这儿一模一样

📌 **顺序建议**：先手动给**一台**测试设备填上，验证解析对了，
**再**去改主路由的下发。反过来做的话，配错了就是全屋解析不了。

### 局域网 DNS 是个隐蔽的单点

不管架在哪台机器上，它一停，**所有指向它的设备都会解析失败**。

对用户来说，症状**不是**"某个服务打不开"，而是"**网断了**"——
因为浏览器打开任何网站都卡在 DNS 超时。多人环境下这意味着
"重启一下服务器"变成"得通知所有人"。

**降低办法**：在主路由下发**备用 DNS**，指向公共 DNS 或主路由自己。
这样你的 DNS 挂掉时，内网域名解析不了，但**上网不受影响**——
故障面从"全断"缩小到"内网服务暂时用不了"。

→ 多人环境下的停机代价见 [`ops/handover.md`](../ops/handover.md)

## 与其它层的交互

### 与层 4（如果你有代理）

**透明代理的 fake-ip 会吃掉你的内网域名**，让它解析成假地址。
配好内网域名之后**必须**把这个后缀加进 fake-ip 过滤列表。

→ [层 4 · 坑一](../pitfalls/proxy-dns.md#之一--局域网服务访问不了)

这是本手册里最常见的"配好了但访问不了"，而症状（502 / 连接超时）完全不指向 DNS。

### 与层 6（如果你要外网访问）

同一个域名，**内网解析到内网 IP、外网解析到公网入口**——这叫分离解析。
好处是内外用同一个地址，客户端不用切换。

⚠️ 两边要**分别配、分别验**。只测了一边就上线，是很常见的疏漏。

## 验收

**分两类做，缺一不可。** 电视和机顶盒上跑不了 `nslookup` ——
**不要把命令行步骤标成要在电视上执行**，那只会让你退回自己的开发机然后宣布通过。

### 第一类：有终端的客户端（电脑、能开终端的手机）

```yaml
verify: |
  # ★ 在另一台电脑上执行，不是服务器本机

  # 1. 名字能解析，且解析对了
  nslookup service.example.com
  # 期望: 返回服务器的真实内网 IP
  #      【不能】是 198.18.x.x（被 fake-ip 吃了）
  #      【不能】是公网 IP（分离解析配反了）

  # 2. 名字能访问
  curl -s -o /dev/null -w '%{http_code}\n' https://service.example.com
  # 期望: 200 或 401
```

### 第二类：没有终端的真实设备（电视、机顶盒、游戏机）

**用它自己的 App 或浏览器访问，观察结果。** 这类没有命令可跑，
所以要写出**可观察的成功标准**：

| 设备 | 怎么测 | 期望 |
|---|---|---|
| 电视 / 机顶盒 | 用它的浏览器或对应 App 填入内网域名 | 能打开、能播放，不是"找不到服务器" |
| 游戏机 | 在网络设置里手动填 DNS 后测试连接 | 连接测试通过 |
| Android 手机 | 用浏览器和目标 App 各访问一次 | 两者都能打开——**App 和浏览器的解析路径可能不同** |
| 智能音箱等 | 看它依赖的服务是否恢复正常 | 功能可用 |

⚠️ **每类设备至少测一台真机。** 内网寻址最典型的失败就是"在我这儿好好的"，
而翻车的恰恰是这些设备——**它们又正好是最需要好记地址的那些**。

⚠️ 只做第一类就宣布通过，会完整地漏掉本层反复强调的那个故障。
