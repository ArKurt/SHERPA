# 锚点 C · NAS 底座

> ⚠️ **这条路径没有实际落地验证过。** 它来自一次完整的方案调研（原文见
> [`archive/`](../archive/)），推理链条完整，但**没有真机跑过**。
>
> 前两条锚点是"这么干过，代价是这些"；这一条是"应该这么干，但你是第一个"。
> 用它的时候把这个差别放在心上。

## 配置向量

```yaml
arch:      x86_64                # 取决于 NAS 型号
substrate: [vm]                  # 厂商虚拟化套件
gateway:   vm-openwrt            # 单臂旁路由，独立 IP
proxy:     nikki | shellcrash    # 按订阅格式二选一，见下
storage:   [internal]            # NAS 本来就是存储设备
ingress:   （另议）
services:  （NAS 厂商的容器套件）
```

## 什么条件下选它

- 已经有一台支持虚拟化的 NAS，不想再添设备
- NAS 常年开机——这是它相对笔记本/台式机的最大优势

## 选型结论

### 用厂商的虚拟化套件，不要用容器

调研里对比过三条：

| | 做法 | 结论 |
|---|---|---|
| **A** | **虚拟化套件 + OpenWrt 系 VM** | **主路径** |
| B | 容器 + macvlan/独立 IP | 备选，仅在装不了 VM 时 |
| C | 特权容器 + host 网络 | **否决** |

C 被否决的理由：host 网络让代理直接接管 NAS 自己的网络栈，与 NAS 本身的职责打架，
且没有独立 IP 可指。→ [层 2](../layers/2-gateway.md#container-macvlan--只在跑不了-vm-时)

### 代理栈按订阅格式选

这条**不是功能偏好，是省事程度**：

- 订阅已经是 Clash / mihomo YAML → `nikki`
- 订阅格式未核实，或来自只给节点列表的客户端 → `shellcrash`（转换能力更强）

→ [层 3](../layers/3-proxy-stack.md#选型的第一判据是订阅格式不是功能)

## 这条路径特有的风险

### 风险一：NAS 重启 = 全屋断网

旁路由跑在 NAS 上，就把网络的可用性绑在了 NAS 的维护节奏上：
固件更新、RAID 重建、盘故障、套件升级——**每一个都会波及全屋网络**。

而 NAS 的这些事件往往不由你安排（自动更新、盘突然告警）。

**这是选这条路径前最该想清楚的一件事。** 如果不能接受，考虑把旁路由放到别的设备上。

### 风险二：厂商套件的不可控性

虚拟化和容器都是厂商套件。固件大版本升级时，套件的行为、网络模式、甚至可用性
都可能变。这不是假设——**这类变更历史上发生过**。

### 风险三：内核不是你的（只在走容器备选时）

容器共用 NAS 的内核。厂商精简过的内核可能缺透明代理需要的模块，
症状是"装上了但起不来"，且报错往往指向别处。→ [层 2](../layers/2-gateway.md)

## 落地前必须自己验证的

因为没有实测，这些**你得自己确认**，不要信本页的推理：

- [ ] 你的 NAS 型号 + 当前固件，虚拟化套件是否可用
- [ ] 有没有你需要架构的 OpenWrt 系镜像
- [ ] 虚拟化套件能不能给 VM 桥接一个**独立的局域网 IP**（不是 NAT）
- [ ] NAS 自己的网关**不要**指向这个 VM（避免开机死锁 → [层 1](../layers/1-substrate.md)）
- [ ] 按 [层 2 的推进顺序](../layers/2-gateway.md#推进顺序关键)分步走

**验证过程如果和本页描述不符，以现场为准，并告诉用户这条路径未经验证。**
