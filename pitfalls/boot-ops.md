> 相关：[`ops/boot-persistence.md`](../ops/boot-persistence.md) ·
> [`ops/migration-retirement.md`](../ops/migration-retirement.md)
>
> 这几个坑的共同点：**平时完全看不出来**，等到重启或换机器那天才爆发。

## 幽灵路由：退役设备留下的影子

**这是本手册里最难诊断的一个坑。**

### 症状

- 某些访问**间歇性**失败，另一些正常
- 在终端里手动 `curl` 同一个目标——**是通的**
- 但服务进程访问它，日志里是"没有到主机的路由"
- 重启服务偶尔"好了"，过一会儿又坏
- 完全不可复现

### 原因

一台设备已经关机退役了，但**别的机器上还留着指向它的配置**——
通常藏在一个**平时不用的网络接口**里（比如 Wi-Fi 的手动网关设置），
而日常走的是有线口，所以没人注意到。

系统据此建立了一条指向不存在设备的路由。**不同进程的路由选择优先级不同**，
于是这条残留路由只影响其中一部分——你手边的那个 shell 未必和出问题的进程走同一条路径。

真实案例里，这条残留藏在 Wi-Fi 的手动配置里，而故障表现在**完全不相干的反向代理**上，
排查还先错判了一轮。

### 修法

直接看路由表，找有没有指向已经不存在的设备的条目：

```sh
ip route | grep <退役设备IP>          # Linux
netstat -rn | grep <退役设备IP>       # macOS/BSD
grep -rn <退役设备IP> /etc            # 配置文件里的硬编
```

⚠️ **macOS 特别注意**：每个网络服务（Wi-Fi、以太网、Thunderbolt）的手动配置是**分开的**，
要逐个查，不能只看当前在用的那个。

### 教训

> **不要只看"能不能 ping 通"。** 你手边的 shell 未必走同一条路径。
>
> 退役一台设备时，**清理所有指向它的残留和退役本身一样重要**——
> 见 [`ops/migration-retirement.md`](../ops/migration-retirement.md) 的退役清单。

## 两个虚拟机实例抢同一块磁盘

### 症状

虚拟机行为异常，磁盘可能损坏。`ps` 一看——**有两个虚拟机进程**。

### 原因

虚拟机命令行用了"后台化/守护化"选项（`-daemonize` 一类）。
进程 fork 到后台，**服务管理器就失去了真正的子进程**。

管理器以为程序已经退出，于是按重启策略又拉起一个——而原来那个还在跑。
两个实例抢同一个 IP 和同一块虚拟磁盘。

### 修法

让虚拟机以**前台进程**运行，由服务管理器直接持有它。
崩溃重启策略只对**异常退出**生效，不要对正常退出重启——
否则你主动关掉它，它又起来了。

### 相关

停机也要注意：直接杀掉虚拟机等同于**拔电源**，来宾系统的文件系统可能损坏。
正确做法是通过虚拟机的管理接口发关机请求，等来宾自己退出，超时才强制终止。

## 重启后服务没回来，但登录后一看又都正常

### 症状

远程重启机器后，服务全都访问不了。等你登录上去检查，
`docker ps` 一看——**全都在跑**。

### 原因

容器的重启策略配对了，但**容器运行时本身需要登录后才启动**
（桌面应用形态的运行时常是这样）。

于是"重启后服务没回来"是真的，而你是**登录之后**才去看的，所以看到的是正常状态。

### 修法

确认容器运行时是**系统级**自启，而不是登录后才启动的用户级应用。

## 冷启动后服务全不可用，有人登录一次才好

### 症状

断电恢复后，**这台机器上"本该自己回来"的东西一个都没回来**。
到机器前登录一次，全部恢复正常。

按这台机器承担的职责，你看到的症状不同：

| 它跑着什么 | 你看到的 |
|---|---|
| 旁路由 / 网关 | 全屋网络不通 |
| 组网工具（远程访问入口） | 从外面连不上这台机器 |
| 相册的自动备份 | 手机传不上去，而且不报错 |
| 常驻 AI harness / 定时任务 | 它们那段时间根本不在 |

**做不做旁路由都会撞上这条**——只要机器开了全盘加密。

### 原因

宿主机开了 **FileVault**。开机后、有人解锁之前，机器停在解锁界面——
**整个启动都排在解锁后面，什么都没在跑。**

### 换成系统级服务也绕不过去

卡住的不是用户会话，是解锁本身。改成 LaunchDaemon 只改变服务在启动完成后
什么时候起，不改变启动能不能开始。

推论：**远程重启这台机器是危险操作**——它可能停在解锁界面等着，而你远程进不去。

### 修法

先查这台机器有没有例外可用——**Apple 芯片 + macOS 26 起可以 SSH 远程解锁**，
那样这个坑就不成立了。判据见
[`ops/boot-persistence.md`](../ops/boot-persistence.md#全盘加密会限制自恢复能力)。

用不了例外的话：要么接受它（并把这个限制**在部署时就告诉用户**，
而不是等第一次断电后才发现），要么把旁路由放到一台不加密的设备上。

⚠️ 这一条是 **macOS + FileVault** 的行为。BitLocker 和 LUKS 各有各的解锁语义，
别照搬。

## 定时任务静默不跑

### 症状

备份、清理、DNS 更新这类定时任务，某天开始就没再跑过。**没有任何报错。**

### 原因

两种常见成因：

1. **机器睡了，或者关了。** 这两种情况的结果**不一样**，而且还要看你用的哪类调度——
   `cron` 一律跳过；launchd 只有 `StartCalendarInterval` 睡醒会跑；
   systemd 的日历 timer 睡醒会补、关机期间要 `Persistent=true`。
   **而且补跑常常是多次错过合并成一次。** 对照表见
   [`ops/boot-persistence.md`](../ops/boot-persistence.md#错过的定时任务会不会补跑)
2. **任务本身失败了** —— 盘满了、路径变了、凭证过期了，而没人在看

### 修法

- 会睡眠的机器上不要放关键定时任务，或者先解决电源策略
- 给备份这类任务加一个"多久没成功"的检查，哪怕只是每月手工看一眼文件时间戳

### 教训

> **静默失败比报错危险。** 报错至少你会发现。
