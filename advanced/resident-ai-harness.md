# 高阶 · 常驻 AI harness

> 把 AI 客户端 / agent 常驻在服务器上：放哪台机器、怎么不被睡眠杀掉、
> 以及代理层要怎么配合。
>
> **本章可选。** 不需要常驻 AI 就整章跳过。
>
> 本章讲的是**常驻客户端与 agent 框架**，不是本地模型推理。
> "在家里跑 AI"这句话常见有两个意思，**先分清是哪个**：
>
> | 意思 | 是不是本章 |
> |---|---|
> | 常驻一个 AI 客户端 / agent 框架，随时能用 | ✅ 本章 |
> | 用自己的显卡跑模型 | ❌ **本手册不覆盖**，需要独显，是另一件事 |
>
> 用户说得含糊时，**问清楚**——两者的硬件前提差着一个数量级。

## 为什么这章对你 读这份手册的 agent 特别相关

如果这台旁路由要给 AI agent 用——包括正在读这份手册的你——
那么本章的分流部分是**功能前提，不是优化项**。配错了，你自己就干不了活。

## 一、放哪台机器：先做一个解耦

常驻类工作和重推理类工作的需求**正好相反**：

| | 常驻（网关、定时任务、长连接） | 重推理（大模型、批处理） |
|---|---|---|
| 要求 | **一直在**、低功耗、可靠 | 算力强、可以按需启动 |
| 频率 | 7×24 | 偶尔 |
| 硬件 | 弱机器就够 | 要好硬件 |

**把它们放在同一台机器上，就得同时满足两边的要求**——
既要 7×24 常开，又要有强硬件，成本和功耗都不划算。

### 解耦形态

```
常驻在低功耗机器上（就是你的服务器）
       │
       │ 需要重推理时
       ▼
  唤醒那台强机器 → 干活 → 让它睡回去
```

唤醒用 [`../ops/wol.md`](../ops/wol.md)。

**这个解耦的好处是省下的不只是电费**——强机器不常开，它的风扇、硬盘、
以及"一直开着总会出事"的概率都降下来了。

---

## 常驻 × 睡眠：一对硬矛盾

**低功耗和"一直在"是矛盾的，没有两全的配置。**

如果服务器要跑常驻 AI：

- 它**不能进深度睡眠**——长连接会断，定时任务不会触发
- 而阻止睡眠意味着持续耗电、持续发热

### 更麻烦的是：这台机器可能同时是旁路由

它睡了，**指着它的客户端全断网**。这时"常驻 AI 需要它别睡"和
"旁路由需要它别睡"是同一个要求，反而简单了——**明确选择常开**。

### 必须先确认的

在配任何常驻服务之前，先回答 [`00-probe.md` Q6](../00-probe.md#q6-这台机器会关机或睡眠吗)：
**这台机器的电源策略是什么？**

不要配完之后才发现它每晚睡觉。那时症状是"半夜的任务都没跑"，
而且要过几天才有人注意到。

## 三、代理层配合：地区钉死

**AI 服务的地区限制比大多数服务严格**，而失败方式往往是静默的。

已知：**Anthropic（Claude）屏蔽香港**，OpenAI 也有类似的地区限制。

如果你的代理兜底走"自动选择"组，而自动组按延迟挑节点——
延迟最低的往往就是离你最近的地区。**某天它漂过去，服务静默失效，
而没有任何人改过任何配置。**

### 做法

给 AI 服务单独建组、手工指定地区、组里**不放自动选项、不放被屏蔽的地区**。

完整方法见 [层 4 · 地区敏感服务](../layers/4-routing-dns.md#地区敏感服务必须钉死出口)。

### 域名清单照官方 allowlist 写，别抄社区规则集

真实教训：某广泛使用的社区规则集里，Claude 相关只有 3 条、一年多没更新，
**漏掉了负责 OAuth 令牌刷新的那个域名**。

后果不是连不上——是"**用着用着掉登录**"。几乎不可能联想到分流上。

各家 AI 服务商都在文档里公布了需要放行的域名清单
（搜 `<服务名> network configuration` 或 `firewall allowlist`）。
这类服务的域名少而稳定，**照官方清单写死后缀，比引入一个会过期的外部依赖可靠得多**。

### 旁路由上没法按进程分流

"只让 AI CLI 走代理，别的直连"——**这个需求在旁路由上做不到**，
旁路由拿不到源主机的进程身份。只能按域名分流。

要按进程分流就得在客户端做。→ [层 3 · 坑 ②](../layers/3-proxy-stack.md)

## 四、排查陷阱：先剥掉环境变量再下结论

**这个坑值得单独讲，因为它会让你错怪旁路由。**

很多启动 AI CLI 的包装器 / 启动脚本会**给会话注入代理环境变量**
（`HTTPS_PROXY` / `https_proxy`），指向一个本机端口，并用**自签证书**做中间人。

于是：在那个会话里 `curl` 某个域名 → 证书验证失败 → 看起来像"代理在 MITM"。

真实案例里，这个现象一度被归因为旁路由的透明代理在做中间人。
后来剥掉环境变量直连验证，证书完全有效——**旁路由从头到尾没碰过它**。
真凶是启动包装器自己的会话代理。

### 排查顺序

```sh
# 1. 先看这个会话里有没有被注入代理
env | grep -i proxy

# 2. 剥掉它再测
env -u HTTPS_PROXY -u https_proxy -u HTTP_PROXY -u http_proxy \
  curl -sI https://<目标域名> | head -3

# 3. 两者结果不同 → 问题在会话层，不在网络层
```

> **通用教训**：诊断代理问题时，**先确认你测的是哪一层**。
> 会话环境变量、系统代理设置、旁路由透明代理是三层不同的东西，
> 症状很像但修法完全不同。搞错了会去改一个根本没问题的组件。

## 五、各 harness 的具体形态

### ChatGPT / 桌面端类

桌面应用形态的 AI 客户端要常驻，注意：

- 它需要**图形会话**——无头服务器上跑不了，或需要虚拟显示
- **与系统空闲睡眠冲突**：桌面应用常驻会阻止睡眠，或者被睡眠打断，二选一
- 更新机制通常是自动的，可能在不合适的时候重启

### 常驻 agent 框架（OpenClaw / hermes 等）

以**守护进程或网关形态常驻**的 agent 框架。OpenClaw 和 hermes 都属于这一类，
形态相近，下面的要点对它们通用。

**为什么适合放在服务器上**：这类框架的价值恰恰在"一直在"——
它要能随时接收任务、维持长连接、按计划触发。这正是低功耗常开机器的定位，
而不是那台跑重推理的强机器（见本章第一节的解耦）。

要点：

- **开机自恢复是硬要求**，不是可选项。一次断电之后它就该自己回来，
  而不是等你发现"怎么好几天没动静了"。
  → [`../ops/boot-persistence.md`](../ops/boot-persistence.md)
- **长连接对网络稳定性敏感。** 如果它跑在旁路由后面，
  **旁路由每次重启都会打断它**——而旁路由恰恰是你会频繁调整的那个组件。
  考虑让它直连主路由，或者接受这个代价并确认它能自动重连
- **睡眠会静默吃掉计划任务。** 机器睡着时到点的任务**未必会补跑**，
  补不补看调度器（`cron` 跳过、`launchd` 补但会合并、`systemd` timer 要
  `Persistent=true`），而且哪种都不报错。→ 本章第二节
- **出口地区。** 如果它调用的模型服务有地区限制，兜底链路漂移会让它静默失效。
  → 本章第三节
- **凭证管理。** 这类框架通常要持有 API 密钥。
  **绝不要把它的配置文件放进任何会同步或备份到公开位置的目录**，
  也不要写进版本库。→ [`../ops/backup.md`](../ops/backup.md)

> **具体装法看各自的上游文档。** 这类项目迭代很快，把安装步骤抄进手册，
> 半年后就是错的。本节只写那些**跨框架、跨版本都成立**的部署考量。
