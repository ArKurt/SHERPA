# 层 5 · 存储

> **本层不推荐任何一种形态。** 硬件条件差异太大，推荐"你该买什么"就是误导。
>
> 但不推荐 ≠ 不给判据。下面每种形态都标了"能承载什么 / 绝不能承载什么"——
> 那些不是偏好，是"否则会坏"。

## 一条贯穿全层的判据

**把数据分成两类，分别安置：**

| 类别 | 特征 | 对存储的要求 |
|---|---|---|
| **状态数据** | 数据库、索引、服务配置 | 苛刻：要原生文件系统、要稳定不掉线、要能保证写入顺序 |
| **体积数据** | 照片原图、影音、下载 | 宽松：大就行，掉一下不致命 |

**状态数据通常比你以为的小**——[锚点 A](../blueprints/a-single-laptop.md) 上
十几个服务的配置卷加起来不到 1 GB。**但别把这个数字当通用值**：
Immich 现行文档说它的 Postgres 文件通常就有 1–3 GB。
按你要装的那几个服务各自的官方说明加现场实测来预留，别照抄别人的数字。

真正通用的是另一半：**它一旦损坏，服务就起不来了。**

> **一个代价很高的错误：把数据库和媒体库放在同一块外接盘上。**
> 那块盘是为"大"选的，却承担了"苛刻"的职责——本手册的素材里就有一次因此
> 反复重启的事故。它证明的是**故障域要分开**，不是"这是所有人最常犯的错"。

## 枚举

| 值 | 形态 |
|---|---|
| `internal` | 机器内置盘 |
| `usb-portable` | 外接移动硬盘（USB 供电或单盘位） |
| `das-enclosure` | 外接硬盘柜（多盘位，独立供电） |
| `nas` | 网络挂载（另一台 NAS，走 SMB/NFS） |

四种可以**混用**，而且实践中通常就该混用。所以配置向量里 `storage` 是**多值字段**，
有几块写几块。

---

## 先读这一节：文件系统决定了这块盘能干什么

**这一节对上面四种形态一律适用**，不管盘是内置的、USB 的、硬盘柜里的还是网络挂载的。
**形态决定"掉不掉线"，文件系统决定"能承载什么"，两件事都要过。**

### 三类用途，要求递增

| 用途 | 例子 | 要求 |
|---|---|---|
| **只读媒体** | 影音库、只读挂载的图集 | 最宽松，exFAT / 网络挂载都行 |
| **可写媒体** | **相册的上传目录**、下载目录、同步目录 | 需要 POSIX 权限 —— exFAT 有条件，见下 |
| **状态数据** | 数据库、索引、服务配置 | 最苛刻 |

> ⚠️ **"媒体"不等于"只读"。这是本层最容易踩的一步。**
> 相册的照片库看起来和影音库一样是"一堆大文件"，但**它是容器要以非 root 身份
> 持续写入的目标**，而影音库通常只读挂载。
> 同一块 exFAT 盘，挂给影音服务只读没问题，挂给相册当上传目录就要先解决属主问题
> ——**不一定要格式化，见下一节。**

### 文件系统对照

| 文件系统 | 只读媒体 | 可写媒体（容器写入） | 状态数据 / 数据库 |
|---|---|---|---|
| ext4 / btrfs / xfs（Linux 原生） | ✅ | ✅ | ✅ |
| APFS / HFS+（macOS 原生） | ✅ | ✅ | ✅ |
| NTFS | ✅ | ⚠️ 跨平台驱动差异大 | ⚠️ 不建议 |
| **exFAT** | ✅ | ⚠️ **只能全卷统一属主**，见下 | ❌ **不行** |
| 网络挂载（SMB/NFS） | ✅ | ⚠️ 看挂载参数与服务要求 | ❌ **多数服务官方禁止** |

### exFAT 的限制到底在哪

exFAT 的限制是**分层的**，不要压成一句"exFAT 不行"——那会把人推去格式化，而格式化会擦盘。

| 限制 | 依据 | 谁会撞上 |
|---|---|---|
| 不存**逐文件**属主与权限位 | 格式本身没有 POSIX owner / mode 字段 | 需要 `chown` / `chmod` 的服务 |
| 没有硬链接 | Linux 驱动 `fs/exfat/namei.c` 的 inode operations 没有 `.link` | 靠硬链接做去重或原子替换的服务 |
| 基础格式无日志 | 事务安全语义属于另一个 TexFAT 扩展，Linux 不实现 | 数据库——异常关机后可能损坏 |

**但"容器写不进去"不在这三条里，它是能解决的。**
Linux exFAT 驱动支持 `uid=` / `gid=` / `umask=` / `dmask=` / `fmask=` 挂载参数
（`fs/exfat/super.c`），可以把整个挂载点映射成某个 UID/GID 可写。

| 你要拿这块盘干什么 | 结论 |
|---|---|
| 只读媒体 | ✅ 直接用 |
| **一个**容器写入媒体文件（下载目录、单用户上传目录） | ⚠️ **可行**：按目标容器的 UID/GID 挂载，然后做写入验收 |
| 多个服务 / 多个用户共写同一块盘 | ❌ 全卷只有一个属主，无解 |
| 服务需要 `chown` / `chmod` 或硬链接 | ❌ 无解 |
| 数据库、索引、服务状态 | ❌ **不放**，另找落点 |

exFAT 的存在理由是**跨平台通用**。如果这块盘要在多台机器间搬，它有价值——
代价就是上面这张表。

**写入验收怎么做**（★ 从容器里跑，不是从宿主）：

```sh
docker compose exec <服务> sh -c 'touch /挂载点/.wtest && rm /挂载点/.wtest' && echo OK
# 期望: OK
# 宿主能写不代表容器里能写——容器以非 root 身份运行，而 exFAT 的属主由挂载参数一次定死。
```

> **手上是一块 exFAT 盘、又要跑相册怎么办？按这个顺序，别跳步：**
> ① 先查该服务官方有没有点名不支持 exFAT（Immich 的 Postgres 就是明确不支持的）；
> ② **数据库一律另找落点**，这条不让步；
> ③ 若只是媒体文件的写入，先按容器 UID/GID 挂载并跑上面的写入验收；
> ④ 只有 ③ 不成立（多服务共写、需要 `chown`、官方点名不支持）才考虑重新格式化——
> **格式化会擦掉盘上现有数据，属于 `needs_human`，必须问用户。**

## `internal` · 内置盘

| | |
|---|---|
| **能承载** | 全部——数据库、配置、系统。这是最可靠的落点 |
| **不能承载** | 只有容量限制，没有语义限制 |

**判据**：状态数据一律优先放这里。**它通常比体积数据小一两个数量级**
（具体多少按服务查，见本页开头），别为了"整齐"把它跟媒体一起挪到外接盘上冒险。

**注意**：容量吃紧时先看能不能只把**体积数据**外移，而不是把整个服务目录搬走。

---

## `usb-portable` · 外接移动硬盘

| | |
|---|---|
| **能承载** | 媒体库、下载、冷备 |
| **本手册不放** | **状态数据（数据库、索引）** —— 见下，这是风险边界 |

### 为什么

USB 外接盘除了盘体老化，还要**单独评估意外断连**——线松了、供电不稳、
主机睡眠时总线掉电、系统更新后驱动变了，直通进 VM 的话还多一层。
这几条和介质寿命无关，也不会体现在 SMART 上。

对媒体文件，掉一次就是"这个视频暂时播不了"。
对数据库，掉一次可能就是**文件系统损坏**，而数据库还在往里写。

[锚点 A](../blueprints/a-single-laptop.md) 上真发生过：盘一走，数据库进入
崩溃重启循环，累计几千次——而**原始数据一个字节都没丢**，SMART 也全绿。
坏的不是盘体，是它上面被反复异常断电磨损的文件系统。

> 这是**一次**事故（当时的系统与数据库版本没记下来），不是每块 USB 盘、
> 每种数据库的必然结局。本手册据此把状态数据挡在 `usb-portable` 之外，
> 那是一条**风险边界**，不是一个已被证明的普适后果。

→ 完整案例见 [坑典](../pitfalls/storage.md#数据库和媒体库同盘盘一走就崩溃循环)

### 文件系统同样要看

移动硬盘出厂常是 exFAT 或 NTFS。**掉线风险和文件系统限制是两回事，都要过一遍**——
见[上面的公共小节](#先读这一节文件系统决定了这块盘能干什么)。

### 如果只有这一块盘

那就**把数据库留在内置盘上，只把媒体文件放外接盘**。这是本层最重要的一句话。

⚠️ **前提是这个服务支持拆分——逐个查，别假设。** 优先选官方明确支持
"配置/数据库在一处、媒体库在另一处"的服务。碰上不能拆的，本手册这条路径
对它不适用，另想办法或换服务。

## `das-enclosure` · 外接硬盘柜

| | |
|---|---|
| **能承载** | 媒体库、大容量数据；**取决于文件系统**，可能也能承载数据库 |
| **绝不能承载** | 落在 exFAT 上的数据库（见下） |

独立供电、多盘位、通常总线更好——**但这些不自动等于更可靠**。
柜体、盘、桥接芯片、线路各有各的脾气，稳不稳要在你自己这套上验收。
形态上的优势要靠下面两件事才拿得到：

### 分职

一柜多盘时给每块盘明确职责，而不是当成一个大池子：媒体一块、照片一块、
数据一块、冷备一块、备份目标一块。职责清晰后，某块盘出问题时你知道影响面在哪。

### 文件系统选型

见[上面的公共小节](#先读这一节文件系统决定了这块盘能干什么)——
**多盘位不会让 exFAT 变得能跑数据库。** 形态好不等于文件系统合格。

> ⚠️ **USB 直通进虚拟机多一层交接**（宿主 → VM 的设备移交）。
> 宿主直接挂载、再以目录方式共享给需要的服务，少这一层。
> 哪种更稳要在你的虚拟化栈上实测——本手册只指出多出来的这一层在哪。

## `nas` · 网络挂载

| | |
|---|---|
| **能承载** | 媒体库、归档、备份目标 |
| **本手册默认不放** | **数据库** —— 但这是风险政策，不是文件系统定律，见下 |

### 为什么默认拒绝

网络文件系统（SMB/NFS）在**文件锁定**和**写入顺序保证**上与本地文件系统语义不同，
而数据库依赖这些语义保证一致性。跑在网络挂载上不一定立刻炸，
**但断连或抖动时可能静默损坏**——这正是最难发现的失败方式。

### 但"任何数据库都不行"是不对的，逐个查上游

| 上游 | 怎么说 |
|---|---|
| **SQLite** | 警告网络文件系统的同步与锁实现各家不一，**错误的锁实现曾导致数据损坏** |
| **Immich** | 明确要求其 Postgres 数据 *never a network share of any kind* |
| **PostgreSQL** | **明确允许把数据目录放 NFS**——但带条件，见下 |

PostgreSQL 那两个条件必须一起满足，缺一条这个许可就不成立：

1. **客户端以 `hard` 挂载**。官方原话是 *"The only firm requirement for using NFS
   with PostgreSQL is that the file system is mounted using the `hard` option."*
   代价是网络出问题时进程会无限期挂起，**所以还得配监控**。
2. **NFS 服务端开 `sync` 导出**。否则客户端的 `fsync` 不保证真的落到服务端的
   持久存储，官方说后果 *"could cause corruption similar to running with the
   parameter `fsync` off"*。

> 📌 **所以本层的规则是：NAS 上的数据库默认拒绝，但这是可以推翻的。**
> 要推翻，得三件事都做到——**所选服务与数据库的上游明确支持**、
> **上述挂载/导出条件逐条满足**、**做过一次拔网线的掉线验收**。
> 三条缺一，就按默认走。
> ⚠️ 反过来也别只记住"上游允许 NFS"——**条件不落实，那句许可就不适用于你。**

### 其它注意

- **延迟**：媒体扫描、缩略图生成这类**大量小文件**操作，在网络挂载上会被往返延迟
  明显拖慢。**慢多少要用你自己的 NAS、协议和数据集测**——本手册不预填倍数
- **断连**：挂载点消失时，正在读写它的服务行为难以预测。挂载参数要考虑超时与重连
- **启动顺序**：服务启动时挂载可能还没就绪。需要显式的依赖或等待

## 组合示例（不是推荐，是说明判据怎么用）

假设：一台机器，内置盘 500 G，外接一块 4 T 移动硬盘。想跑相册和影音。

```
内置盘 500 G
├── 系统
├── 所有服务的配置与数据库          ← 状态数据，全在这
└── 缩略图/转码缓存（可重建，掉了不心疼）

外接 4 T
├── 照片原图
└── 影音库                        ← 体积数据
```

**关键点**：相册服务的数据库在内置盘，它的照片库在外接盘。
这样拆，外接盘的故障就**波及不到数据库**——盘掉线时服务会报"找不到文件"，
难看，但数据库还在。如果数据库也在外接盘上，掉一次就可能要从备份恢复。

⚠️ **但"插回去就恢复"要自己证明，别预先承诺。** 服务会不会自动重新发现挂载点，
各服务不同——用本页的[拔盘演练](#验收拔盘演练)验一次，那才算数。

## 备份

家用场景可以说"以后再说"。**工作室 / 微型企业不行——那里数据丢失等于停业。**

最低限度：

- **状态数据**（数据库、配置）定期导出，存到**另一块物理盘**上。这部分小，代价很低
- 很多服务自带定时数据库备份功能，**先确认它开着**，再考虑外部方案
- **备份要验证能恢复。** 没试过恢复的备份不算备份

详见 [`ops/backup.md`](../ops/backup.md)。

## 验收

存储这一层有两类检查，**别混**：结构检查确认"摆对了"，验收确认"扛得住"。

### 结构检查（在服务器上跑，装服务之前）

```sh
# 1. 数据库落点的文件系统类型
df -T <数据库目录>                                    # Linux
diskutil info "$(df <数据库目录> | tail -1 | awk '{print $1}')" \
  | grep 'File System'                               # macOS
# 期望: 原生文件系统（ext4/btrfs/xfs/APFS），不是 exFAT，不是网络挂载

# 2. 数据库落点不是外接易掉线的盘
lsblk -o NAME,TRAN,MOUNTPOINT | grep <挂载点>          # Linux
# 期望: TRAN 不是 usb
```

### 验收：拔盘演练

```yaml
verify: |
  # ★ 只有在还没有真实数据时做才安全 —— 之后就没机会了。
  #   在【另一台设备】上观察结果，不要只看服务器上的日志。

  # 1. 基线：从客户端确认服务正常
  curl -s -o /dev/null -w '%{http_code}\n' http://192.0.2.10:<端口>
  # 期望: 200

  # 2. 卸载外接盘，再从客户端看
  # 期望: 服务仍然响应，报的是"找不到媒体/文件"
  #      【不能】是数据库崩溃、502、或整个服务挂掉

  # 3. 重新挂载，从客户端确认自行恢复（不需要手工重启服务）
  curl -s -o /dev/null -w '%{http_code}\n' http://192.0.2.10:<端口>
  # 期望: 200，且数据都在
```

⚠️ **第 2 步是整层唯一真正的验收。** 它证明的是：外接盘掉线时，
损失是"暂时看不到媒体"而不是"要从备份恢复数据库"。

⚠️ **做这个演练要主动制造一次故障。** 有真实数据之后没人敢做——
于是你永远不知道盘掉线时会发生什么，直到它真的掉线那天。
