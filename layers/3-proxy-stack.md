# 层 3 · 代理栈

> 装哪一套透明代理。这一层有一条绝对约束和一个几乎人人会踩的坑。

## 绝对约束：只装一套

**绝不并装两套透明代理。**

两套会各自往防火墙里塞流量劫持规则，互相覆盖、互相打架。症状是"两个插件的面板都显示
运行中，但客户端连不上任何东西"——因为流量被 A 劫走、按 B 的规则处理，或者反过来。

这个故障极难诊断：每个组件单独看都正常。所以它写成 `conflicts` 硬约束，不是建议。

> 想换栈？**先彻底卸掉旧的**（包括它写进防火墙的规则和开机自启），确认防火墙干净，再装新的。

## 枚举与选型

| 值 | 内核 | 订阅格式 | 何时选 |
|---|---|---|---|
| `nikki` | mihomo | **只吃 Clash / mihomo YAML** | 订阅已经是 Clash 格式；想要现代、轻量的 LuCI 界面 |
| `shellcrash` | mihomo 等 | 吃得杂，转换能力强 | **订阅格式未核实、或来自只给节点列表的客户端** |
| `openclash` | mihomo | Clash 系 | 要最全的功能和最强的规则表达力；代价是重 |
| `homeproxy` | sing-box | sing-box JSON | 订阅是 sing-box JSON 且转不了 Clash 时 |
| `client-side` | 各客户端 | 各自 | 不做旁路由，或需要按进程分流 |
| `none` | — | — | 只要旁路由的其它能力 |

### 选型的第一判据是订阅格式，不是功能

这一点反直觉，但实践中最省事：**先确认你的订阅链接返回什么**，再选栈。

> ⚠️ **订阅 URL 是凭证。** 探测它的格式时，**不要把它写进命令行参数** ——
> 同机任何能看进程列表的人都能读到，而且它会进入 shell 历史和 agent 的调用记录。
> 见 [`ops/secrets.md`](../ops/secrets.md#怎么传给服务)。

**安全的探测方式**（URL 只经环境变量传入，原始响应绝不回显）：

```sh
# 1. 用户自己把链接放进环境变量，不要让它出现在你的命令里
read -rs SUB_URL && export SUB_URL          # 输入时不回显

# 2. 只输出【格式分类】，不输出任何响应内容
curl -s --max-time 15 "$SUB_URL" \
  | head -c 2000 \
  | grep -qE '^(proxies|proxy-providers|mixed-port|port):' && echo "clash-yaml" \
  || curl -s --max-time 15 "$SUB_URL" | head -c 2000 \
     | grep -qE '"outbounds"' && echo "sing-box-json" \
     || echo "node-list-or-unknown"

# 3. 用完立刻清掉
unset SUB_URL
```

> **如果你是 agent**：你的最终产出只能是 `clash-yaml` / `sing-box-json` /
> `node-list-or-unknown` 这个**分类结果**。
> **不要把完整 URL、也不要把响应内容写进回复、日志或任何文件。**
>
> 做不到这一点（比如你的执行环境会记录完整命令），就**让用户自己在本地看一眼格式**
> 再告诉你分类，不要接收这条链接。

| 返回 | 说明 | 指向 |
|---|---|---|
| YAML，含 `proxies:` 或 `proxy-providers:` | Clash / mihomo 格式 | `nikki` 可直接吃 |
| 一大串 base64 | 节点列表，不是完整配置 | `shellcrash`，或先做格式转换 |
| JSON，含 `outbounds` | sing-box 格式 | `homeproxy`，或转 Clash |

有些机场对**同一个 URL** 会按请求头返回不同格式。换个 User-Agent 再试一次，
往往能直接拿到 Clash 版，省掉整个转换环节。

**优先级**：向服务商要 Clash/mihomo 链接 → 同 URL 换 UA → 才考虑自建转换服务。
转换服务意味着你的订阅要经过第三方，能自己解决就别引入它。

## 装完先确认：裸核模式是关的

代理插件普遍有一个"只启动内核"的模式（裸核 / core only / 仅内核）。
原型阶段验证内核时很方便，**切到旁路由时极容易忘记关掉**——
而它会让插件的防火墙劫持规则**全部不生效**。

症状极具迷惑性：**路由器上自测代理端口能出海、返回 204，客户端却国内外全断。**

> **「核能出海」≠「客户端能借道」。**

这是本手册最常见的静默失效，也是所有 `verify` 都要求从客户端视角写的来源。
完整案例、集成件确认清单见
[坑典 · 裸核模式](../pitfalls/proxy-dns.md#裸核模式核能出海客户端全断)。

## 选型判据：旁路由拿不到进程身份

**旁路由上按进程分流（`PROCESS-NAME` 一类规则）不工作。**

这不是配置问题，是原理问题：旁路由看到的是**转发流量**，它只知道源 IP 和目标，
不知道那个包是源主机上哪个程序发的。有的插件干脆把进程匹配默认关掉。

**这条直接决定了选型**，所以放在这里而不是排障区——它不是"出错了"，
是"这个方案做不到这件事"。

### 影响

"让终端走代理、浏览器直连"这类需求，**在旁路由上做不到**。只能按域名和 IP 分流。

### 正确的分工

| 需求 | 该在哪做 |
|---|---|
| 电视、游戏机、IoT——设备本身装不了代理 | **旁路由**（这是它存在的理由） |
| 按域名/地区分流，全设备统一策略 | **旁路由** |
| 按进程分流（这个程序走代理，那个直连） | **客户端** |
| 临时开关、频繁改规则 | **客户端** |

两者**不是二选一，是分工**。常见的成熟形态是：旁路由兜底管住装不了代理的设备，
工作机上另装客户端做精细分流——但**工作机要么走旁路由、要么走本机客户端，不要叠加**
（叠加会绕出难以预测的路径）。

## IPv6：全屋代理绕不开的一问

**如果目标是"全家默认都走代理"，这一节不能跳。**

### 为什么它会咬人

代理插件默认接管的通常只有 IPv4。而如果客户端**同时有一条能用的 IPv6 默认路由**，
那么访问双栈站点时，系统可能优先走 IPv6 —— **直接出网，绕过整个旁路由**。

症状是**"同一个站点时好时坏"**：两次访问走了不同的协议族，一次被代理、一次直连。
这类故障不可复现，而且完全不指向 IPv6。

⚠️ **只测了 IPv4 就宣布"全屋代理完成"，结论超出了你实际测过的范围。**

### 先探测

见 [`00-probe.md` §7](../00-probe.md#7-ipv6-现状)。没有 IPv6 默认路由就跳过下面。

### 三种处理方式

| 方式 | 做什么 | 什么时候选 | 代价 |
|---|---|---|---|
| **A · 关掉 IPv6 下发** | 在**主路由**上停止下发 IPv6 地址/路由，让客户端只有 IPv4 | 最简单可靠，家用绝大多数场景够用 | ⚠️ **要动主路由，触及铁律①**——告诉用户怎么做，不代劳。且会失去 IPv6 的好处 |
| **B · 让代理也接管 IPv6** | 代理栈同时监听并劫持 IPv6 | 你确实需要 IPv6，且插件支持 | 配置复杂度上一个台阶；**本手册没有验证过这条路径** |
| **C · 明确放行直连** | 承认 IPv6 不走代理，并**告诉用户哪些流量会绕过** | 用户能接受"部分流量直连" | ⚠️ 那就**不是"全屋代理"**了，必须说清楚 |

> **本手册只对 A 和 C 给判据。** B 涉及各插件的具体实现差异，
> 而手册的素材里没有经过实测的 IPv6 透明代理案例——
> **不会凭推理写一套步骤让你去别人机器上试。**
> 走 B 就以你所选插件的官方文档为准，并按下面的验收自己证明它成立。

### 不管选哪种，验收都要分族做

见本页的[验收](#验收)第 4 条。**两族分别证明**，不要只测一族就收工。

## 安装要点

不同插件的具体命令差异大且随版本变，**以官方文档为准**。这里只列跨插件通用的注意事项：

1. **先确认架构对得上**。下错架构的包，症状是"装上了但内核起不来"
2. **优先用官方软件源**，而不是发行版打包的一键脚本。后者版本往往滞后
3. **装完先别灌订阅**。先确认插件本身能起、面板能开，再灌配置。
   两件事一起做，出问题时分不清是谁的错
4. **确认开机自启**，否则一次重启就回到解放前

## 验收

```yaml
verify: |
  # ★ 在一台【客户端】上执行，网关已指向旁路由

  # 1. 国内直连站点
  curl -s -o /dev/null -w '%{http_code}\n' http://<国内站点>
  # 期望: 200/204

  # 2. 需要代理的站点
  curl -s -o /dev/null -w '%{http_code}\n' https://<被代理的站点>
  # 期望: 200/204

  # 3. 确认走的是预期出口（不是直连、也不是漏到别的链路）
  curl -s https://<回显 IP 的服务>
  # 期望: 出口 IP 落在你选的节点所在地区

  # 4. ★ 两个协议族分别证明（目标是"全屋"时必测）
  curl -s -4 https://<回显 IP 的服务>
  curl -s -6 https://<回显 IP 的服务>
  # 期望，按你在「IPv6」一节选的方式：
  #   方式 A（关掉下发）→ -6 应当【失败】（客户端没有 IPv6 路径）
  #   方式 B（也接管）  → -6 的出口应与 -4 一致
  #   方式 C（放行直连）→ -6 走直连，且你已明确告知用户这部分不经代理
```

第 3 条不能省 —— 前两条通过只证明"能上网"，不证明"走了代理"。
直连也能让它们返回 200。
