# 锚点 B · 混合

> 服务栈直接跑在宿主上要性能，旁路由单独留一个轻量 VM 要体验。
> **两套都要维护，但每一处都在它该在的地方。**

## 配置向量

```yaml
arch:      aarch64               # 也适用于 x86_64
substrate: [bare-metal, vm]      # 不互斥，这正是「混合」的含义
gateway:   vm-openwrt            # 单臂旁路由，独立 IP
proxy:     nikki                 # mihomo 内核
storage:   [internal, das-enclosure]
ingress:   tunnel + port-forward # 隧道为主，一条直连口给大流量媒体
services:  [jellyfin, navidrome, aria2, sunshine-moonlight,     # 原生跑
            immich, home-assistant, vaultwarden, sunpanel]     # 容器跑
           # 实机上另有聚合搜索、漫画库等，本手册未收录
```

## 什么条件下选它

- 机器性能足够，不想让服务栈白白多套一层虚拟化
- 服务里有对 I/O 或硬件加速敏感的（媒体转码、照片机器学习）
- 能接受维护两套东西

## 为什么这么分

选型时摆在桌面上的是三条路：

| | 做法 | 结论 |
|---|---|---|
| A | 整个平移进 VM | 最接近原状，但服务栈白白多一层虚拟化 |
| B | 全部原生，不做旁路由 | 性能最好，但**丢掉"全屋无感"体验**，且在 macOS 上做透明网关很别扭 |
| **C** | **服务原生 + 旁路由轻量 VM** | **两边的甜点，代价是两套都要维护** |

选 C 的决定性依据是**预检**：先逐个查了所有要用的容器镜像有没有目标架构的构建，
确认全部原生可跑——**服务栈根本不需要 VM**。

> **这个顺序值得学**：先查清楚"不套 VM 行不行"，再决定架构。
> 反过来（先决定套 VM，再发现其实不用）会白白背上一层复杂度。

## 落地时的关键动作

### 分两步走，不要一次到位

```
① VM 先起在隔离网络（NAT）里，验证系统能起、代理内核能装能跑
   —— 对局域网零影响
        ↓ （中间隔了一天）
② 切桥接，拿独立 IP，成为真正的旁路由
   —— 安排在白天、有人在场、能物理接触机器的时候
```

第②步是整个部署里最危险的一步。**不要在晚上、不要在远程、不要在家人正用网的时候做。**

### 宿主双网口

有线口做桥接与服务，Wi-Fi 留作**管理生命线**——桥接操作会中断有线口，
有第二条路才不会失联。

### 宿主自己不走 VM

宿主的默认网关指向主路由，**不指向跑在它自己身上的旁路由**。
否则开机时 VM 没起来 → 宿主没网 → 死锁。

## 代价

### 代价一：两套要维护

宿主的系统更新、VM 的固件升级、两边的服务，节奏不同。没有捷径。

### 代价二：宿主的电源策略会波及全屋

**旁路由跑在一台会睡眠的机器上是个矛盾**：它睡了，指着它的客户端就断网。
睡眠与唤醒策略必须先解决，这不是可以"以后再说"的事。

### 代价三：磁盘加密让开机自恢复不完整

这台机器开了 FileVault。**在有人解锁之前，机器停在解锁界面，什么都没在跑**——
所以"未登录状态下旁路由可用"这个承诺给不了。做成系统级服务也绕不过去，
卡住的是解锁本身。

⚠️ **这条锚点定型时还没有 SSH 远程解锁。** Apple 芯片 + macOS 26 起，
开了「远程登录」的机器可以在重启后从远程解锁——**同样的硬件，这个代价可能已经不成立了**。
判据和另一个例外（`fdesetup authrestart`）见
→ [`ops/boot-persistence.md`](../ops/boot-persistence.md#全盘加密会限制自恢复能力)

### 代价四：踩过的两个坑

- **裸核模式没关** —— 从隔离网络切桥接时忘了改回来，症状是"路由器自测能出海、
  客户端全断"，折腾数小时。见 [层 3 坑 ①](../layers/3-proxy-stack.md)
- **组网工具的域名被 fake-ip 吃掉** —— 必须在切网关前解决。
  见 [层 4 坑 ②](../layers/4-routing-dns.md)
